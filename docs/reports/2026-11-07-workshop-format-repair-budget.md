# 分卷格式修正导致的二次输入超限

## 已确认原因

任务 `52482a7186d0`，revision 27。保存的第 1 次最终回复及请求收据在 `stage-responses/27-1.json`，本轮未改写。用当前部署前代码、实际会话与保存回复在禁网容器中回放，精确复现：

| 阶段 | 含封装预留的输入字节 | 结果 |
| --- | ---: | --- |
| 全局故事设计第 1 次请求 | 121,082 | 已发送并收到回复 |
| 第 2 次格式修正 | 128,565 | 超过本地 128,000 上限，未发送 |

模型返回的 `narrative_format` 把完整合同放进了额外的 `multi_volume` 键内。解析器只看外层，因此将实际存在的字段报为缺失。原系统参考示例也使用按 mode 索引的外层对象，同时要求“返回此对象”，容易造成误读；无法从日志证明模型的内部原因，但此处的接口歧义确实存在。

随后协调器把完整创作上下文、刚收到的完整故事回复、错误和修正要求一起重发，增加 7,483 字节。此前骨架阶段投影覆盖了普通请求，没有解决这一修正路径的增长。这是系统修正流程缺陷，不是单本剧情问题；接近连接上限的其他分卷或系列作品也可能触发。会话继续使用冻结的 Genre/Tag，未意外读取刚更新的活动文档。

## 修复

1. 已知 mode 的参考示例直接提供合同对象，明确禁止额外 mode 包装；章节规划不再附带全局阶段专用的分卷输出示例。
2. 解析边界仅拆开唯一、与外层 mode 一致的包装，内部值不改变。多个包装、mode 冲突、缺字段和不连续分卷仍走完整验证，不能靠“容错”掩盖。
3. 将“故事有效但分卷合同无效”与“故事本身无效”分开。前者通过独立的 `NarrativeFormatRepair` 请求，只提交当前全局故事、待修合同、格式定义、错误及受保护字段，不重新提交全部历史、来源和写作说明。
4. 修正回复只允许 `narrative_format`。程序持有原始故事并合并这一个字段；组织形式、章节数、目标字数、有效卷边界、系列身份、确认状态受代码保护。完整阶段重新验证后才保存检查点。
5. 共用原来的两次修正上限、任务截止时间、取消机制和私有原始回复收据；不增加无限重试。真正的故事字段缺失仍需要创作上下文，不把它伪装成纯格式修正。

没有提高网关上限、压缩故事文字、替换冻结 Tag 或改写历史骨架。格式修正的上下文范围在提示中明确说明；它不等同于重新审阅来源或证明文学质量。
