## 实现边界

- `core/planning_coordinated.py` 定义 `coordinated-repair-v1` 纯合同。依赖计划逐项覆盖原问题，分类为矛盾、衔接缺口、解释争议或原作冲突。章节问题必须绑定原章节；章节解释争议也必须读取该章。原作冲突进入 `source_conflict`，停止并保留结果供作者决定。
- `core/planning_coordinator.py` 先确定需改章节与只读依赖，再分组修订。显式依赖和自动相邻章节存在读写交叉时合并为同组，避免两组分别把对方待改章节当成旧的只读依据。计划、各组响应、修订候选及复核分别保存，完整旧回复不会在恢复时被重新生成。
- 修订返回完整受影响章节，并以原章规范 JSON 的 SHA-256 作为前置条件。所有问题必须给出明确处置与原文引述；声称修正的问题必须对应实际改动。递归保留原有字段、列表/场景数量下限、ID、来源引用和字数预算；执行合同结构、枚举、布尔及数值不可改变，允许源文支持的叙事文本澄清。结构检查不能证明语义保真，因此后续核查仍是必要门禁。
- 可选全局改动仅限已列入修订范围章节的既存 `chapter_map` 叙事字段：`purpose`、`incoming_consequence`、`outgoing_commitment`。使用原完整映射的 JSON 路径及精确旧值；映射未按章号排序时也不会错改。人物身份、全局结局、分类、其他合同和作者源文不在可改范围。
- 缺少转场时，可在源文已确定的前后事件之间补最小衔接，不能借机新增重大人物决定。`interpretation` / `recheck` 只是交给复核的解释，不会自动撤销问题或认定通过。需要作者决策的响应不应用任何局部补丁。

## 输入容量与完整性

依赖规划读取完整采用源文和已声明的全局不变量，明确不提供候选章节正文和派生 `chapter_map`；它不能声称已检查被省略的候选。分组修订提供全部其他全局字段、完整选中章节与路线图条目、相邻及显式依赖，并声明远处章节/条目的省略范围。服务端仍保有完整原候选，哈希和修改前置条件一律对完整候选验证。原文投影按完整章节边界选择，不摘要、不截断段落；无法可靠识别边界时回退到完整来源。

`core/planning_repair_context.py` 在任何分组修订发出前预检全部组。费用相关请求按实际系统提示、完整冻结创作上下文及封装预留计数，复用现有容量协商，不任意提高网关上限。超限时停止并保留成果，不拆散一个协调组、不省掉证据来勉强发送。逐阶段格式纠正仍最多一次，格式纠正的完整请求也重新检查容量。

全局/章节生成缓存身份保持不变；新修订使用独立策略和上下文哈希。恢复资格检查验证源文、brief、创作锁、原全局、每批前序依赖、完整章数及首轮核查绑定；存在已消耗的修订记录时，刷新页面或升级不能重置次数。任务摘要与恢复入口采用相同恢复判断。

## 修订后的核查

组内结果先通过既有 `_batch` / `_global` 合同检查，随后在完整候选上执行原有核查与最终结构门禁。复核同时携带原始问题、修订计划和处置理由；不接受修订模型自我宣布通过。

`core/planning_review_reuse.py` 只复用绑定原始候选、**此前已通过**且完整输入上下文和核查指令均完全相同的窗口。任何全局设计、来源、章节、覆盖范围或修订证据变化均会使复用失效。旧阻断结果不能作为通过凭据。新窗口与精确复用窗口共同覆盖全书；没有添加正文全文阅读评分环节，也没有撤销既有来源、身份、情绪、结局和商业合同检查。
