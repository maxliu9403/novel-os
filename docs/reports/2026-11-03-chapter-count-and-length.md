# 章节数选择与每章篇幅约束

2026-11-03，已部署 localhost:5174。适用于启用故事容量规划、尚未确认篇幅的讨论；已确认执行合同不被自动改写。

## 行为

每章字数设置作为**分章目标的规划上限**。需要扩展故事时优先增加章数；不会为满足原章数暗中增大章长，也不削减已确认故事。正文仍使用既有章长浮动与质量检查，不在字数线上截断文本，本轮没有新增正文绝对字数上限。

方案卡同时显示总篇幅、当前章数、平均每章和最长一章。用户可以选择新章数；数学起点为 `ceil(总篇幅 / 每章规划上限)`，最多 511 章。数字仅说明容量可容纳，不保证该章数下的自然断章一定可行。

当前作品展开版 16,800 词、每章设置 1,100 词，默认建议从 16 章开始，平均约 1,050 词。原紧凑版虽平均 1,100 词，最长章仍达 1,250 词，因此也需要重新分配；不能只凭平均数合格就采用。

作者点击“按 N 章重新安排”后才调用模型。该轮仅安排自然分章和场景分段，保留全文作者上下文及原方案，不重新讨论故事走向、不生成骨架、不修改原始每章设置。新方案保存后再次供作者采用，随后走现有骨架生成与正文启动流程。

## 实现与边界

- `core/capacity_partition.py` 验证精确章数、逐章上限、总量不变、全部原场景顺序及连续分段、原场景总预算范围。不能新增/删除/重排场景；模型负责提出自然断点。
- 原场景名称、来源引文、表现方式、读者价值、理由均保留；可选 `partition_label` 说明新段落。未使用该字段的旧计划序列化不变，已保存候选及合同哈希兼容。
- `api/workshop_repartition.py` 验证当前提案哈希、来源、会话版本、操作范围和章数可行范围。来源绑定后的失败请求可由作者明确重试；重复 HTTP 请求复用任务，不重复购买调用。错误不会自动触发格式修复或全故事推演。
- 重分章沿用同一 worker、持久状态、取消及请求诊断；刷新后仍可看见进行中任务，失败后保留原方案和约束。基础设定/故事变化清理旧重分章请求，不能在新的设定上重放。
- 服务端禁止直接采用超每章设置的未确认方案。真正采用后冻结完整分章合同，并把章数、各章目标传给骨架与已有正文规划流程。平均值不再覆盖用户的每章设置。
- 重分章不新增故事方案卡或地图，也不凭该动作确认故事假设。模型给出的分段文字仍是编辑方案；结构和预算校验不证明文学质量。
