# 头脑风暴 900 秒超时：CLI 输入传递阻塞

## 现场证据

讨论 `d7c6589ce293` 第 3 轮的请求 ID 为
`d62bb77d53354a2e8e15d37ec37e4eea`。北京时间 2026-10-08 13:51:50 启动，
14:06:50 超时。原始诊断文件：

```text
docker-data/workshop_v2/d7c6589ce29349ae99121b5f771fd6d1/diagnostics/3-brainstorm.jsonl
```

- 系统输入 137,370 字节，用户输入 2,143 字节。
- 进程启动后直到 900 秒超时，阶段一直是 `input_transfer`。
- 没有 `stdin_sent`、CLI 事件或重试记录；stdout/stderr 均为 0 字节。
- 最终结果文件不存在。进程存活不能证明模型正在推理。

## 原因

可暂停的 CLI 调用原先通过管道写入提示词，每 0.1 秒调用一次 `communicate()`。
第一次传入提示词；遇到 `TimeoutExpired` 后，后续调用传入 `None`。

实际部署使用 Python 3.11.17：其 `_communicate()` 只有在本次传入 `input` 时
才重新注册 stdin 写入。如果 CLI 启动较慢、输入超过管道容量，首个 0.1 秒无法
写完，后续轮询便不再继续发送。CLI 等待输入结束，父进程等待 CLI 输出，最终
耗尽整个 900 秒预算。这是应用输入传递死锁，不能解释为模型思考过久。

本地虚拟环境使用 Python 3.14，其实现会继续发送已缓存的输入，因此以前的
本地检查没有暴露这个部署版本差异。

## 修复

`LLMClient._run_cancellable_cli()` 先将完整 UTF-8 输入写入匿名临时文件，
复位文件位置后直接交给子进程作为 stdin。后续只轮询 stdout/stderr，避免
依赖短超时后恢复管道写入的解释器行为。

保留原有总超时、取消检查、进程组清理及诊断；输入文件随调用退出关闭，
不额外持久化提示词。`stdin_sent` 现在表示输入与 EOF 已可供子进程读取，
不表示 CLI 已消费输入或模型已接收请求。

## 验证

- 在原部署的 Python 3.11.17 中，用延迟 0.35 秒读取 stdin 的本地程序和
  140 KB 输入复现旧逻辑阻塞，2 秒截止后超时，无输出。
- 同一容器加载修复后，延迟读取 420 KB UTF-8 输入约 0.4 秒完成；字节数和
  SHA-256 一致，确认完整交付，没有重复或丢失。
- 新增回归覆盖延迟读取大段 Unicode/CRLF、Python 3.11 管道恢复语义、暂停、
  超时、启动失败、准备输入时取消或写入失败，以及文件和线程清理。恢复旧逻辑
  的反向检查确实失败，避免只在 Python 3.14 上得到假阴性的测试结果。
- 202 项相关回归通过。所有模型调用均为本地模拟；上述耗时是输入传递验证，
  不是模型生成速度。
- 已用 `./deploy.sh up` 更新原有 5174 服务。部署后的 Python 3.11.17 容器
  直接运行同一 420 KB 输入检查，0.39 秒通过；`/api/health` 返回 200。
  原讨论仍为第 3 版、三条历史输入，没有自动发起新的模型请求。

原讨论和历史输入保留；模型、推理级别、提示词以及 15 分钟预算均未调整。
