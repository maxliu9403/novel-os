# 原图精修：容器参考图读取失败修复

## 原因与影响范围

`repair-task-717fea70cd2f431cb9fbccb035c5ea4d` 的原图文件完整，SHA 与批准方案一致。失败发生在 Codex 图片工具读取 `referenced_image_paths` 时：容器不允许创建文件沙箱所需的用户命名空间，`bwrap` 在读取图片前退出。外层 Codex 进程仍可能以 0 退出，原处理只给出模糊的 `exit 0` 错误。

这是该容器环境下 Codex **按文件路径精修**的通用兼容问题，不是候选图 2 损坏或故事提示词不合格。普通文字生图和 API `/images/edits` 不走此参考文件读取路径。

这次任务约 8 分 16 秒包括约 7 分 11 秒方案规划，以及约 1 分 5 秒图片阶段；不能把总时间都算作图片生成时间。

## 修复

- Codex 精修通过 app-server 的结构化 `image` 输入发送冻结原图的 data URL，并设置 `detail: original`。不再使用会缩放并附带本地路径标签的 CLI `--image`。
- 新建临时会话，只附一张原图，图片工具用 `num_last_images_to_include=1` 引用会话图片，避开第二次文件沙箱读取。保留 `workspace-write`，没有放宽容器或 Codex 权限。
- 单个精修请求只启动一次 turn，不自动重试、不退化成文字生图。输出必须对应唯一成功的图片工具回执；失败、超时、未调用图片工具、返回原图均不能伪装成精修成功。
- 明确禁用 `omit_app_server_notification_media`，保证成功回执包含原始图片字节。0.153 默认已关闭该功能，此显式设置用于防止其他用户配置改变返回格式，不涉及沙箱权限。
- 增量识别参考图沙箱错误，及时停止，并保留最终可取得的宿主文本 token 累计值，避免重复累计。
- 原图、其他候选、正式选择和原失败任务保留；新结果仍进入原有另存版本、排版和 A/B 审核流程。

## 验证边界

实际部署容器使用 Codex 0.153.0。临时配置下可复现 `bwrap` 命名空间权限失败；本地假模型服务验证结构化图片输入在首个 Responses 请求中保持 **2048×3072 原尺寸、完全相同的 SHA、无图片路径标签**。旧 CLI 输入在同一实验中变为 1280×1920。

官方对应版本源码中，`num_last_images_to_include` 从已有 `InputImage.image_url` 构造编辑请求，不调用文件读取；`referenced_image_paths` 分支才调用此次失败的文件沙箱。[Codex 0.153.0 图片工具源码](https://github.com/openai/codex/blob/rust-v0.153.0/codex-rs/ext/image-generation/src/tool.rs)

假 API-key provider 不公布图片生成工具，因此本轮未完成实际图片端点的端到端出图验收，亦未调用真实模型或重试用户任务。协议测试使用成功、失败、超时、退出竞态和回执绑定的模拟事件；不能将它们表述为真实精修效果验收。
