## 3. 优先排查的兼容差异

1. **动态分类 v2。** 外层协议仍是 V4，但分类已经支持发行方自定义 Genre/Tags。如果 H5 仍用固定 `novel-types.2026-10` 字典校验所有包，会拒绝这类成品。需并行保留旧 v1，并新增 v2 解析；不能丢弃未知标签或把 v2 假装成 v1。
2. **历史语言标签。** 本包是 `英文`，并非 `en` 或 `en-US`。H5 若只接受语言代码，需要明确的历史别名映射；不能默认中文，也不能猜错后继续。
3. **整包导入入口。** 应识别根目录 manifest 和 sidecar，再进入 EPUB。不能用旧逐章 Markdown 上传器处理本包，也不能把外层交接资料 ZIP 当成小说 ZIP。
4. **上传网关与业务校验分层。** 实包约 12.31 MiB，低于 Novel OS 的 64 MiB ZIP 合同上限；若网关提前返回 413，需要核查 H5 入口大小限制。当前没有 H5 HTTP 响应，因此这只是排查项，不是已确认原因。

H5 预检应明确声明支持 `novel-classification.v2` 和 `novel-taxonomy.v1`。Novel OS 报告中的 `engine_contract_status: passed` 只说明导出合同通过，`external_import_status` 仍为 `pending`。

## 4. 文件角色与字段落库

以下相对路径是样本实际路径。实现应优先按 manifest 的角色和显式指针定位，验证双方指向同一文件，不能只靠文件名猜测。

| 来源 | H5 映射及规则 |
|---|---|
| `package-manifest.json` | 文件索引；核对 path、role、media_type、size、sha256；解析 `book_id` 和包修订 |
| `meta/h5-import.json` | 绑定 EPUB、章节稳定 ID、全书章号、卷、非正文、作者及组件版本 |
| EPUB OPF `dc:title` | 书名；不得作为去重键 |
| sidecar `author` | 作者展示名；manifest 同时提供时必须相同；旧包依次回退 manifest、EPUB `dc:creator`，都缺失则保留数据库现值；按字段是否存在判断，不按真假值判断 |
| EPUB OPF `dc:language` | 原始语言；校验后做明确的历史别名映射 |
| `meta/publication-copy.json.spoiler_free_blurb` | H5 现有 Synopsis/简介字段；本包与 OPF `dc:description` 相同；旧包没有发行文案时可读取 OPF description |
| `publication-copy.hook_lead` | 独立宣传钩子；不能覆盖 Synopsis |
| `publication-copy.reader_heading` | 导读标题，不是书名 |
| `meta/novel-classification.json` | 主 Genre、Tags、公开目录快照、受众频道、长度属性 |
| `meta/novel-serialization.json` | 分卷、系列绑定；读者目录展示卷名及章节范围；结构剧透字段只用于后台，不直接作为读者简介 |
| sidecar `chapters[*]` | 书章稳定 ID、正文顺序、卷绑定及 XHTML 定位 |
| sidecar `non_chapter_items[*]` | 独立 Introduction；不作为付费章、免费章或普通章 |
| sidecar `cover.selected` | 本次选中封面；本包 `replace`，从该描述符读取独立图片并核验 |
| `covers/cover-set.json` 与候选图片 | 后台候选及选择关系；未选中候选不能自动变成读者封面；生成提示等运营字段不向读者展示 |
| `book.md`、PDF、DOCX、`h5-publication/*` | 其他交付表示及旧出版投影；不作为第二份正文导入 |

本包 Synopsis 含字面量 `\n\n`。如 H5 需要段落换行，可在显示层对这个历史字段进行明确兼容；不能先全局替换转义字符再校验文件 SHA，也不能修改存档原件。

### 正文与章节定位

正文唯一来源是 sidecar 指向的 EPUB。读取 `META-INF/container.xml`，定位 OPF；用 `item_id`、`href`、`zip_path`、`spine_index` 与 OPF manifest/spine 对照，再核对原始 XHTML 的 `xhtml_size` 和 `xhtml_sha256`。EPUB 内 `novel-os:chapter-map` 也需一致。

真实包第 1 章：

```json
{
  "chapter_id": "novel-os:fa82979d0b85440f986fdc9a491424c4:chapter:1",
  "number": 1,
  "kind": "chapter",
  "volume_id": "volume_01",
  "chapter_in_volume": 1,
  "epub": {
    "item_id": "c1",
    "href": "chap001.xhtml",
    "zip_path": "OEBPS/chap001.xhtml",
    "spine_index": 1,
    "xhtml_size": 6416,
    "xhtml_sha256": "593ba5ec3a253e3c9c60ad420e5e09cb21bb897e181b848a5b01d41511ba18a1"
  }
}
```

这是字段摘录，完整对象见 `contracts/real-book/h5-import.json`。`spine_index` 从 0 起，本包 Introduction 占 0，第 1 正文占 1。**不能把 spine 索引加一直接当章号。** 全书正文 `number` 为 1–60，换卷不归零；免费窗口按该章号判断。卷首没有独立正文时不要凭空创建付费章节。

## 5. 动态 Genre/Tags

完整实物见 `contracts/real-book/novel-classification.json`。

- 分类外层为 `novel-classification.v2`；`taxonomy.schema_version`、`catalog_version` 为 `novel-taxonomy.v1`。
- `taxonomy` 包含 namespace、1 个 genre、1–20 个不重复 tags。发行合同不能套用某一新建界面的 1–2 Tags 选择限制；当前历史成品含 6 个 Tags。
- `primary_genre_id` 必须等于 `taxonomy.genre.id`；`story_type_ids` 必须按序等于 `taxonomy.tags[*].id`。v2 不使用旧 secondary/tone/setting 并行数组表达新增标签。
- 目录主键为 `(namespace, kind, id)`；revision 为整数且 ≥1；公开名称/定义保存在目录修订及书籍导入快照中。相同名字不能合并不同身份。
- 同一身份和 revision 内容相同可重复导入；内容不同应报冲突。旧修订不能覆盖较新的全局目录，历史书籍仍保留自己的分类快照。
- namespace 最长 120 字符；ID 匹配 `^(genre|tag)\.[a-z][a-z0-9_-]{1,74}$`。labels 至少有 `zh-CN` 或 `en-US` 一种，每个 1–100 字符；definition 为 1–600 字符纯文本。标签名称、定义均不得作为 HTML 执行。
- 管理台与 H5 读者端的筛选项从服务端目录 API 获取；服务端按稳定 ID 计算筛选、计数、分页；新增 Tag 不应要求前端重新发版。

真实包的 `novel-os.local` 是开发默认命名空间。本轮保留历史产物字节不变。生产发行应协商持久命名空间与导入方权限；若决定更换本书的发行身份，需走正式重新编译与重新验收流程，不能解压手改再塞回 ZIP。

## 6. 身份、更新与原子入库

建议书籍唯一键 `(tenant_id, source_system, source_book_id)`；章唯一键 `(book_fk, source_chapter_id)`，另约束 `(book_fk, number)`；卷按 `(book_fk, volume_id)` 定位。`classification_id`、`serialization_id`、书名、作者、任务 ID、EPUB `dc:identifier` 都不是书籍身份。

导入顺序：

1. 安全检查 ZIP、路径、大小、条目与完整性；解析 manifest 和唯一角色指针。
2. 检查协议能力、文件原字节摘要、EPUB/sidecar/分类/分卷一致性、章节映射和封面。
3. 根据已认证来源和 `book_id` 定位既有书；生成拟创建/拟更新的组件列表。未经校验，不产生可见书章或目录记录。
4. 事务中保存目录修订、书籍及卷、章节 upsert、组件版本和导入回执；媒体先进入临时区，失败时不留下可见残留。
5. 更新时保留既有数据库书章主键，阅读进度、收藏和已解锁权益继续引用原记录。

根据 sidecar `versions` 区分正文 `content_sha256`、非正文 `front_matter_sha256`、封面 `selected_cover_sha256`、候选/选择关系 `cover_metadata_sha256`、作者 `author_sha256`、分类 `classification_sha256`、结构 `serialization_sha256` 和文案 `publication_copy_sha256`。EPUB 字节变更可能只是内嵌元数据变更，不能单凭 `epub_sha256` 判断正文改变。

相同包再次导入应无重复记录。更新封面、作者或分类不能删除重建章节。旧包 A 导入后更新为 B，再上传 A，属于历史重放；应提示恢复历史版本或等待明确选择，不能静默回滚，也不能仅凭旧 receipt 存在就声称与当前版本相同。

本次协议没有中间插章、拆章、删章重排的权益迁移表；遇到这类变化需明确迁移流程，不能自动重编号覆盖已购章节。

### 摘要的层次

- ZIP SHA-256：最终 ZIP 原字节，本说明第 2 节及验收文件使用此值。
- 文件 SHA-256：解压出的文件原字节；XHTML、JSON 都不能先 trim、换行、解码展示转义或重序列化后再计算。
- `package_revision_sha256`：manifest 中有序 `files` 数组的规范 JSON SHA-256，不是 ZIP SHA，也不包含 manifest 自身。
- `import_revision_sha256`：`book_id + versions` 对象的规范 JSON SHA-256。
- 规范 JSON 采用 UTF-8、对象键排序、紧凑分隔符、不转义非 ASCII；数组次序保留。禁止重复键、非有限数字；分类与结构 ID 还有各自字段选择规则，不能拿文件 SHA 直接替代。

目录合同和文件摘要须同时成立；不能为“通过导入”跳过摘要或降低作品原有质量门禁。

## 7. 导入边界与故障反馈

当前 Novel OS 合同边界如下；H5 网关若先于应用限制上传，需要与约定对齐并计算 multipart 开销。

| 对象 | 上限 |
|---|---|
| ZIP | 64 MiB；展开 128 MiB；1024 条目 |
| EPUB | 16 MiB；展开 32 MiB；600 条目；512 个 spine 项 |
| JSON/XHTML | 单文件 4 MiB；JSON 深度 64、XML 深度 128 |
| 出版封面 | PNG/JPEG；单图 8 MiB；单边 ≤8192；像素数 ≤16×1024×1024；最多 24 候选 |

禁止路径穿越、重复路径、符号链接、加密条目及不支持的压缩方式；XML 禁止外部实体/DTD。内嵌正文进入读者端前按安全 XHTML 白名单渲染，不能执行脚本或外部资源。校验原件与安全渲染副本分开保存。

真实包展开为 14,986,896 bytes、79 条目；EPUB 展开为 2,222,744 bytes、68 条目，均在上述范围内。

建议 H5 上传结果区分：上传失败、包校验失败、能力不支持、数据冲突、事务失败、导入完成。返回可定位的 `code`、`path`、实际/预期值和 request/trace ID。接口 URL、状态码及错误枚举由 H5 团队确认；本交接没有虚构一个已上线 API。故意损坏夹具的本地错误为 `file_digest`，H5 如采用不同错误码，应在回执注明映射。

## 8. 联合验收顺序与通过条件

包内 `acceptance/cases.json` 固定测试输入和依赖；免费窗口值只是测试配置，不修改成品商业定价。

1. 最小动态包首次导入：新增 1 本、2 章；动态 Genre/Tags 正确呈现。
2. 同包重复导入：书、卷、章不增加，已种入的阅读进度/解锁/收藏保持。
3. 损坏分类摘要：整笔拒绝，无既有数据变化、无可见孤立条目。
4. 真实成品首次导入：新增 1 本，60 章、3 卷、1 篇非正文；英文正文、Synopsis、作者、封面和 6 个 Tags 完整。Introduction 不占免费窗口。
5. 真实成品重复导入：身份与权益保持，无重复内容。
6. 80 章静态夹具首次导入：旧 v1 分类继续可用；4 卷章节连续，Introduction 不参与收费。
7. 同书只更新封面：正文与 EPUB 摘要不变，数据库书章主键、阅读进度、解锁和收藏均保持。
8. 再次上传封面更新包：幂等。
9. 更新后回放旧包：明确历史重放，未经确认不改当前书。
10. 同结构不同书籍 ID：另建 1 本，不能因正文或结构摘要相同合并。

更新测试前请创建真实测试用户的进度、收藏及至少一项付费章解锁；验证前后主键和状态摘要，而不是只比较页面看起来一样。

此外，H5 发布验收需补：分类同 revision 不同内容冲突、目录旧修订、命名空间冒用、分类/EPUB 不一致、未声明条目、路径与大小边界、事务回滚及中途失败。当前五份技术夹具并不覆盖这些全部负例，不能宣称这些边界已经在 H5 测过。

### 回传什么

将 `acceptance/h5-result-template.json` 按实际结果填写，附 H5 分支/commit、运行版本、目标环境、时间、每份 ZIP 的 SHA-256、HTTP 响应或导入日志、入库数量和身份/权益前后对照。不要将导入 token、用户隐私或数据库凭据放入回执。

如双方要使用 Novel OS 的现有机器验收器：在资料包解压根目录，以 Novel OS 虚拟环境执行其 `scripts/h5_acceptance.py plan --cases acceptance/cases.json` 生成本机计划；计划绑定本机绝对路径，换目录后需要重新生成。H5 再按附带的 `acceptance/importer-receipt.schema.json` 提交对应计划的回执，使用 `verify --plan … --receipt …` 检查声明的一致性。该工具不会自行上传、执行 H5 导入或认证对方日志；最终仍需双方核查实际结果。

资料包不包含 Python 验收器；下面命令需要另有 Novel OS 源码及已安装项目依赖的虚拟环境。替换两个本机路径后执行：

```bash
NOVEL_OS_CHECKOUT="/path/to/Novel-OS"
H5_HANDOFF_DIR="/path/to/NovelOS-H5-Handoff-20261114"
cd "$H5_HANDOFF_DIR"
"$NOVEL_OS_CHECKOUT/venv/bin/python" "$NOVEL_OS_CHECKOUT/scripts/h5_acceptance.py" \
  plan --cases acceptance/cases.json > acceptance/plan.local.json
```

H5 实际运行后，另行生成符合 `importer-receipt.schema.json` 的 `acceptance/importer-receipt.json`，填入该本机计划的 `plan_sha256`。它与便于人工沟通的 `h5-result-template.json` 不是同一种格式。在同一目录执行：

```bash
"$NOVEL_OS_CHECKOUT/venv/bin/python" "$NOVEL_OS_CHECKOUT/scripts/h5_acceptance.py" \
  verify --plan acceptance/plan.local.json --receipt acceptance/importer-receipt.json
```
