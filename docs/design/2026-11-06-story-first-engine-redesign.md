# Novel OS 故事创作工作流与产物标准重设计

日期：2026-11-06。状态：用户已批准；主要工作流已实现并通过离线工程验收，尚未部署或运行真实模型比较。实施范围和验收边界见 [实施记录](../reports/2026-11-06-story-first-engine-implementation.md)。下面的审查证据记录的是改造前状态。

本轮目标是修改整个系统的创作方法、工作流与产物标准，不是修复某一本书，也不是先让 Gemini 重写小说。模型接入只记录兼容性发现，不进入本轮实施范围。

## 1. 设计结论

系统应让模型承担专业故事设计，让作者决定重大方向，让代码管理版本、依赖、状态和交付格式。首要创作产物是作者能读出故事的剧情提案；正文的目标是把提案中的期待、冲突与回报真正写成阅读体验。

当前问题不能归结为模型弱或提示词长。已经找到方向错误、规则冲突与阶段职责混杂。继续叠加“更精彩、更有情绪”的要求不足以解决，必须同时替换相应流程和校验标准。

用户认可的 PDF 是**提案表现力和主动设计能力的参照**，不是要固化其人物、反派、伦理冲突、章数或结局。质量目标也不是所有作品都变成复仇爽文，而是兑现本书承诺的满足感：反击、被理解、心动、真相、成长、幽默或其他有吸引力的体验。

## 3. PDF 为什么更容易让作者感到“有故事”

| 方法 | PDF 中的表现 | 应迁移到系统的能力 |
| --- | --- | --- |
| 先提出可持续发展的整体故事 | 第 1–4 页主动扩展视角、家庭空间、主支线和后续冲突，然后再展开章纲。 | 模型先提出完整、可选的故事路线，作者不必逐个发明剧情。 |
| 将背景变为人物弱点与筹码 | 抚养经历、领养身份、工作和体面家庭都参与后续关系变化。 | 从已有材料寻找可扩展的叙事潜力，不把背景放在档案里闲置。 |
| 用场面表达心理 | 第 11 章的礼物落差、第 20 章强势姐姐卸下伪装、第 21 章信任破裂。 | 写“谁做了什么，另一个人如何回应”，让作者直接看到可写的场景。 |
| 主支线互相改变 | 第 18–20 章婚姻财务线带来牧场主线的新信息与同盟。 | 支线影响主线的行动条件、代价、认知或情感，不只是轮流插播。 |
| 利用信息差产生期待 | 读者、家人、对手知道的事情不同，旧动作因此有了新的含义。 | 区分作者知道、读者知道、人物知道；不把所有秘密一次解释完。 |
| 在压抑中安排回报 | 第 18 章的主动布局、第 20 章的同盟、第 25 章的反击，穿插主线压力。 | 回报有不同形态，读者不用一直等待最后结局才得到价值。 |
| 本章完成一件事，又引出下一件事 | 用户选出的第 20 章先交心与结盟、揭示旧设定的新意义，再以母亲到来开启对质。 | 章末钩子承接本章已经发生的变化，不靠任意截断。 |

其中最值得迁移的是**背景 → 欲望与弱点 → 行动 → 关系／局势变化 → 回报与新期待**。这是编辑观察，不是要求每章照同一个公式填空。

PDF 仍是故事提案，尚不能证明正文、付费率或所有专业细节成立。需要保留其创作胆量，同时修正少数会破坏回报可信度的地方：

- 第 3 页的 61 章以后收束与后文第 30 章结局未协调，应统一容量，不能让最后阶段一笔带过。
- 身世与水源地是可以提出的新设计，但不能声称原文已经写明，或把有歧义的源文解释冒充原作者本意。新提案不需要已有剧情证明；只有“继承事实”的声明需要来源。
- 第 24–29 章的能力跃迁、快速关系修复和资产馈赠，需要为人物自己的行动留出铺垫与贡献。得到帮助可以是回报，不应让所有胜利都由别人赠送。
- 第 18 页的关键医学证明桥段不能作为结局依据；此前专项报告已记录问题。这类局部事实问题应定点替换，不应因此把整本故事改成专业审查报告。

不采纳 PDF 的“某年龄段必哭、必付费、平台必过”式结论。我们采用它可见的场面设计能力，不把其自我评价写成验收结果。详细专项分析见 [PDF 分析报告](../reports/2026-11-05-reference-story-design-review.md)。

## 4. 新工作流：先设计故事，再生成可执行产物

```text
作者构想 / 原故事材料 + 一个 Genre / 多个 Tags
                  ↓
确认创作起点与继承范围
                  ↓
整体故事提案 → 作者选主方向
                  ↓
按故事段落推演：场景化章纲 + 爽点 / 情感回报 + 伏笔
                  ↓
合并成唯一故事设计，检查篇幅与关键因果 → 作者确认
                  ↓
代码生成可读骨架及执行视图
                  ↓
逐章写作 → 联合审稿 → 通过即保存；有必要问题才修订并复核
                  ↓
简介 / 封面交接 / H5 交付包
```

来源阅读仍需覆盖所有提供的章节和 Synopsis；没有资料时不虚构原作后续。它是一次可恢复的前置工作，不在每轮或每章重复全文阅读分析。移除的 M3 全书阅读评议不恢复。

### 4.1 把“参考创作”改成明确的“原故事推演”

三个入口语义清楚分开：原创构想、原故事推演、改编重写。当前“参考创作”入口按本次需求改为原故事推演；不能继续用“参考”同时指代保留原故事和另创人物。

- 原故事推演：默认继承已有角色、关系、已发生事件与世界设定，从已知故事进度向后设计。允许新人物、新秘密、新支线、新对手和艺术化发展。
- 改编重写：明确哪些旧内容保留、哪些可以重新设计。用户同意的变更写入同一版本的决定记录。
- 源文歧义和未读部分保持可识别；模型可以提出新解释与后续，不把它们说成源文事实。
- 需要改变原主角、核心关系、前文关键事件或结局方向时才提出重大选择；人物动作、场景安排等细节由模型设计。
- Genre/Tags 与原故事冲突时说明冲突和可选方案，不能为了符合标签偷偷替换人物或整条主线。

来源读取交接应包含：已读范围及顺序、最后已知事件、人物当前状态与知情范围、关系未决事项、已埋线索、不可改变的作者约束、待创作空间，以及必要原文定位。重要场面保留原文片段用于后续展开；一般分析摘要作为辅助。沿用一次来源阅读任务生成这些内容，不再加一轮独立“审批来源”调用。

来源原文、分析、作者导入的提案分别保存。PDF 是提案参考，不能不加区分地将其中全部改写设想合并为源文事实。新模式必须贯穿讨论、骨架、正文与封面；仅改首轮一句提示不算完成。

### 4.2 头脑风暴从“问卷”改成专业提案

首轮给少量有实质差异的整体路线，通常 2 条足够，作者已有完整方向时直接深化。每条让作者看到：谁的故事、主要冲突如何发展、最值得期待的场面、结局回报与代价。通过代表场面说明，不额外要求一套复杂表格。

选定路线后，模型按开篇／中段／高潮／结局推进当前段落。可默认每轮展开一个自然故事段落，通常约 3–5 章，具体随篇幅调整，不写死章数。作者可以要求多推演、局部重做或直接整理骨架。

一轮只在确有重大分歧时提出一个单选问题，选项必须具体。作者可选择并补充，也可明确委托推荐方案。没有待选大方向时，“继续”就是沿已选路线发展，不再强造一次选择。存在互斥待选方向时不得替作者默选。

人物动机、场景调度、伏笔串联、主支线接法由模型主动设计。不得再让作者逐项证明自己说过开篇、中段、高潮、结局的每一个细节。模型设计完成、作者采纳、正文写成三种状态分别记录；作者委托允许模型设计，不等于模型可以宣称自己就是作者。

界面保留当前阶段、简短全书梗概和待处理重大决定。主区域展示故事，详情折叠显示来源与变化；无需每轮向用户展示完整地图 JSON。收敛标准是整体路线可写、主要选择已定或明确委托、没有阻断性矛盾、篇幅能容纳，而不是五区都凑到逐字作者引文。

### 4.3 Genre/Tags 必须改变故事，不能只变成标签

沿用一个 Genre 与多个关联 Tags 的可维护 Markdown，不新增固定组合模板库。Genre 提供主要阅读承诺与世界／叙事规则；Tags 改变关系张力、阻力、行动机会、回报方向或表达气质。整体提案需用具体场面体现它们怎样共同作用，不能只复述标签定义。

例如狼人元素应影响身体体验、关系选择或群体规则；二次机会需要让破裂原因、重建行动与重新选择参与主线。这是类型说明对故事的影响，不意味着所有狼人书必须使用同一种族群制度，或所有复合必须靠同一种救援。标签有冲突时提出少量可行解释让作者决定；不冲突的专业组合由模型完成。

每个已选标签都要在全书设计中有可辨认的作用，但不要求每章出现全部标签。将作用保存在现有故事设计中，随章卡进入正文上下文，不再另建一套逐章填表协议。验收要问“去掉这个元素，故事是否仍几乎不变”，并给出对应场面，而不是统计关键词出现次数。

## 5. 头脑风暴与骨架的产物标准

### 5.1 作者看到的章节提案

固定四个主字段，沿用用户认可的格式：

```markdown
### 第 N 章：标题

- 叙事视角：人物名；多视角时明确场景切换
- 核心剧情：
  1. 具体事件：人物想获得什么，采取什么行动，对方如何回应。
  2. 冲突推进：行动带来什么阻力、发现或关系变化。
  3. 本章结果：人物做出何种选择，失去或得到什么。
- 看点／爽点：具体的反击、亲近、揭示、情感释放等，以及它回应的前期压力。
- 章末钩子：本章变化之后，读者具体想看什么发生。
```

三条剧情是推荐阅读颗粒度，不是硬性情节数量。静场、余波和终章可以用情感落点替代新危机；不能为凑格式把所有章节写成同一种结构。“看点／爽点”不允许只填“张力拉满”，要说出人物或关系的实际变化。

需要时补一个折叠的“伏笔与回收”：此前哪里埋下、本章如何推进或换义、以后准备在哪里兑现。没有相关线索就不加字段。保留序号、版本和引用作为代码元数据，作者不用填写 ID。

### 5.2 伏笔服务故事，不服务打勾

分别处理事实线索、关系细节与人物承诺。模型可借用已有细节，也可为后续设计新的伏笔；不要求所有反转都能在导入的前五章找到现成证据。

伏笔记录只需要来源位置、读者初始理解、计划中的新解释、预计兑现段落，以及实际正文位置。计划埋设／正文已埋／已推进／已兑现分别记录，不再用“模型声明 paid”单独证明读者已经得到回报。

兑现可以是解决一个问题，也可以重新解释旧关系。新秘密应与既有因果相连；不能为了留存不断新增秘密，却把旧问题无限延期。这里是编辑判断，不设计固定每三章揭一次秘密的全局计数门槛。

### 5.3 唯一故事设计与轻量骨架

作者确认的故事设计是唯一内容源，不再让后续 Architect 另写一套竞争故事。骨架改为六部分：

1. 创作设定与读者承诺：模式、语言、视角、Genre/Tags、篇幅、读者期待。
2. 整体故事：开篇到结局、重要选择和主要情绪回报。
3. 人物、关系与必要世界规则：只保留对行动、理解和关系有意义的内容。
4. 章节提案：采用上述四字段格式，保留已批准的具体场面。
5. 伏笔、回报与尚待决定事项：只记录需要跨章管理的内容。
6. 来源继承与作者决定：哪些来自原文、哪些是新设计、哪些旧设定被明确修改。

内部只保留一套有版本的故事数据。Markdown、前端卡片、正文工作集和封面交接由它生成；不得分别调用模型写一份“大纲”、一份“故事地图”、一份“骨架”并互相校对。

模型负责语义设计；代码负责编号、引用、字段类型、版本、章数与预算计算、视图拼装和哈希。缺失的故事因果不能靠代码补造，缺失数据不能默认通过。机械字段如启动命令、发行字段和散列由代码生成，不占用创作模型推理。

短篇在方向与分章确认后一次整理；长篇按故事段落保存检查点，最后确定性合并。仅新增、冲突或未展开的语义内容需要模型处理，不强制所有作品经历六次格式拼装。

### 5.4 对外简介与内部故事全貌分开

内部整体故事包含结局、伏笔解释和人物真实动机，用来指导写作。对外 Synopsis 是给读者的内容承诺：呈现值得在意的人物处境、核心冲突或关系张力，以及下一步值得期待的问题；不复制内部全书摘要，也不默认剧透终局。

Synopsis 必须体现选定题材及实际采用的故事，不能用不存在的反转吸引读者。允许不同形式：关系对峙、迫近的选择、悬念开场等，不强制每本都套同一个营销句式。讨论阶段可以有草案，正文完成后核对承诺是否兑现；不因改简介重新规划全书。来源书的官方 Synopsis 与本书简介使用不同字段，不能把来源文案原样当成新书产物。

最终产物分工明确：故事设计指导创作；可读骨架让作者审阅；章卡与状态供引擎执行；完整正文供读者阅读；Synopsis 与封面交接供发行。后四者都绑定同一故事版本，关键设计变化会标记受影响产物待更新。代码可检查绑定和完整性，不能替模型补写情节或宣称文学质量已通过。

## 6. 正文引擎：保护提案的吸引力

### 6.1 写手获得的工作集

每章包含：本书创作设定、已批准章卡、该场人物与所知信息、前章结尾及相关已写场面、当前关系状态、到期伏笔／回报、需要保留的连续性事实。全量档案可追溯，按需选择相关内容；投影要记录范围和来源，不宣称有损摘要就是全文。

“需要保持正确”与“需要本章写出来”分别呈现。比如伤势、证词边界、既有合约仍须一致，但除非局势改变，不必让人物每章完整重讲一遍。

既有章卡足够时直接写；只有当前正文导致下一章确需调整，才进行有边界的局部规划。允许非关键调度改进；修改关键情节、原设定或结局必须形成明确变更。

### 6.2 初稿标准

- 核心剧情写成发生中的场面：动作、对白、内心判断、对方反应与后果；不能只把章纲扩写成事件报告。
- 人物允许愤怒、自私、误判、软弱、幽默和冲动。行为有其原因和后果，不要求所有人正确表达边界、冷静协商或用同一种成熟话术。
- 将“爽点”写成获得的体验：实际反击、有效选择、关系靠近、看清真相、能力发挥、尊严恢复等。强度按题材与本书承诺决定，不等于所有章都升级暴力。
- 回报要有展开空间，让读者看见反应与变化；重要胜负不能一句“后来她成功了”略过，也不应刚兑现就被无依据地清零。
- 不在正文解释“这体现了成长”“此处形成情绪价值”；人物的具体经历承担这些作用。
- 遵守作者单章篇幅。故事需要更多空间时在规划期提出加章，不靠临时加长一章或压掉关键场面解决。
- 开篇尽快让读者进入值得在意的处境；后续章节承接前章兑现。安静、幽默、温柔可以成为有效阅读收益。

### 6.3 编辑与核验职责重分配

效率复核后的推荐默认路径：章卡 → 写作 → 联合审稿 → 通过即提交。审稿同时承担 Editor、Continuity、Style 的责任，但先判断是否确实需要修改；无问题不再重写一遍正文。正常章的应用级模型调用目标为一次写作、一次审稿，不含前置规划、失败恢复与必要修订，也不代表供应商内部只发生两次请求。

联合审稿阅读完整当前章和必要连续性上下文，检查场景兑现、人物声音、题材体验、因果与前文一致性，保留各责任的结论。输出简短、带位置和原因的必要问题；通过时不用重复列举全章内容或自报文学分数。合并审稿会增加单次任务负担，必须通过缺陷样本和真实章节比较验证，不能预先宣称与多次审稿等效。

只有确实损害阅读或故事正确性的问题才进入修订：例如已批准的核心场面没有写出来、关键回报被一句概述带过、人物知道不该知道的秘密、关键关系或因果矛盾。可选措辞、不同审美偏好不自动阻塞章节。修订保留已经成立的高光场面和角色声音，不追求人人理性，不按固定压缩比例改稿，不通过大量解释“修复”潜台词。

修订之后必须核验实际最终候选，不能沿用修改前的通过结论。问题范围小且依赖清楚时核对改动及其关联上下文；牵涉时序、人物关系、章末承诺或跨章事实时扩大到整章及相关正文。最终文本与通过结论绑定同一版本。定点修订及复核增加调用，真实总成本必须计入这部分。

自动修订有明确次数、用量和时间预算。达到预算保留初稿、修订稿、问题和进度，显示可恢复状态；不悄悄重新生成整章或整个故事。继续沿用既有任务幂等、取消、检查点和晋级机制。

全书高潮、关键关系转折和结局在章卡中标明重点审稿目的，同一次审稿优先检查其具体回报；不另设逐章阅读评议产品。只依赖写手自检的一次调用方案可作为未来实验对照，不是本次质量优先的默认方案。

### 6.4 替换文学硬校验

| 保持代码强制 | 改为本书相关的编辑判断 |
| --- | --- |
| 结构可解析、章节顺序、稳定引用、文件完整性、正式状态有效 | 固定七类情绪、固定试读情绪顺序 |
| 不把未批准分支当已采用、不伪造作者决定 | 每章都必须主角制造转折 |
| 已知人物事实、时间和关系不能被无声明改变 | 每章必须同一种目标—代价—逆转结构 |
| 声称伏笔已兑现需要对应实际正文，不仅有计划 | 同类钩子出现几次就一律失败 |
| 作者篇幅约束及 H5 正式产物规则 | 所有主题都套家庭劳动、资源证明、边界与制度听证 |

真正的语义矛盾仍需要模型或人工判断，代码本身不能证明没有漏洞。文学检查要求具体文本依据，不能只因一个模型觉得“还不够爽”就判任务失败。

## 7. 面向付费阅读的体验设计

目标是让读者已经获得满意体验，愿意继续获得更多。爽感可以包括胜利，也包括心动、秘密揭晓、被理解、关系确认、掌握主动与有余味的释然；按 Genre/Tags 和作者方向选择。

免费段落要交付代表性故事体验，建立至少一项具体期待，并兑现具有分量的局部问题。付费节点选择在已经发生变化、下一步后果值得期待的位置。不能简单套 PDF 的“第 15 章付费”；平台免费窗口未定时先标候选节点，待产品约束明确再安排。

首个付费章应先承接免费末章承诺的主要事件，不能切到无关支线回避兑现。后续持续让人物付诸行动、获得反馈和回报，不能反复受辱、误会和拖延来增加收费章数。付费前后章均按正常完整章节写作，不靠拆碎章节制造购买。

在现有章卡中记录重点节点的前期期待、本次回报和下一步承诺即可。无需增加一套逐章付费评议任务或所有章节都要填写的新表格。将来实际完读、下一章点击及购买数据用于验证设计，不在上线前承诺转化率。

## 8. 提示词重写原则与核心草案

每个请求只装配四层：本阶段职责、作者决定与当前故事、已选 Genre/Tags 的本阶段指导、本轮必要输出格式。各层只承担一种责任。

删除普通创作请求中的重复角色宣言、全阶段说明、重复量表、历史格式示例和跨阶段工程细节。用户给的丰富剧情不是垃圾输入，不能与重复规则一起裁掉。上下文归档保留原文；工作集包含当前决定、必要原文与待解决问题，明确引用和覆盖范围。

### 头脑风暴核心指令草案

> 你是商业小说的故事设计师。围绕作者选定的读者体验、Genre/Tags 与已有构想，主动设计具体可写、有情绪、有因果、有阶段回报的故事。
>
> 按创作模式处理来源。原故事推演继承已发生的事件、人物与关系，从当前进度发展后续；可增加新秘密、支线、对手和场面。新设计标为提案，不宣称它出自未读原作。需要改变故事身份或关键前史时给作者选择。
>
> 先把整体故事讲清楚；方向已定后直接推进当前段落。重大分歧给具体选项与推荐，专业细节由你完成，不把创作变成问卷。
>
> 章节提案用“叙事视角、核心剧情、看点／爽点、章末钩子”。核心剧情写人物行动、对方回应和实际变化；看点说明读者为何在意；钩子承接已经发生的事。必要时说明伏笔埋设或回收。
>
> 从人物已有经历、欲望、秘密、关系与世界规则发展冲突。让主支线互相影响，让对手有策略，让主角和配角都有有效行动。允许复杂情绪和错误选择，不把所有人写成理性讲解者。
>
> 在压力中安排有依据的回报与喘息，不用重复受辱、突然救星或无止境藏答案维持篇幅。按本书气质安排心动、反击、发现、幽默、亲情或其他阅读满足。
>
> 保留作者已经选择的方向；当前路线足够完整时主动建议整理骨架。状态记录从本轮提案派生，不在回复里复述工程协议或长篇自我评价。

### 正文核心指令草案

> 根据已批准章卡写出可直接阅读的完整正文。重点展开本章最有价值的场面，让人物以自己的欲望、语言与行动相互影响；使用必要的内心判断、潜台词和细节，使读者经历变化。
>
> 章卡中的情绪与爽点是写作目的，不是要打印到正文的分析标签。兑现本章应有的发现、行动或关系回报，给关键变化留下反应与余波，再自然承接下一期待。
>
> 事实约束需要保持成立，不等于每条都要解释。避免所有角色用同一种原则性语言论证自己；也不要删掉真正有力量的坦白、争执或独白。保留前文已经建立的文风与具体关系。
>
> 遵守来源继承、作者重大决定、视角和篇幅；未到时机的秘密不能提前揭示。不能为了满足检查项改写已确认事件或把小说写成事件摘要。

这是方法与职责草案，实际开发应将协议 schema 与创作文本分开维护。不得把本文件整篇重新注入模型，造成下一轮提示词膨胀。

## 9. 工程落地与模块边界

| 责任 | 改造范围 | 完成条件 |
| --- | --- | --- |
| 来源与模式 | `api/source_library.py`、`core/source_study.py`、创建入口及共享来源交接 | 前后端使用同一个模式定义；继承状态一路到骨架、正文及封面；没有残留“另创人物”指令。 |
| 故事讨论与产物 | `api/workshop_request.py`、`workshop_story.py`、`workshop_delivery.py`、`workshop_assembly.py` 与对应界面 | 一套故事数据生成提案、地图、骨架和执行视图；旧六部拼装流程由新入口替换，不再平行叠加。 |
| 类型知识与检查 | Genre/Tags MD、`core/reader_investment.py`、`core/commercial_story.py`、`core/commercial_quality.py` | 类型定义能引导不同阅读体验；移除与通用创作方法冲突的固定文学门槛。 |
| 正文执行 | `core/scene_execution.py`、`core/orchestrator.py`、`core/pipeline_runner.py` 及角色提示 | 复用批准章卡；写作后一次联合审稿；必要时定点修订并核验实际最终候选，保留恢复和成本账目。 |
| 交付 | 既有包生成与 H5 校验器 | 由代码生成正式格式、章节映射及 SHA；不让创作模型猜字段。 |

不追求一次重写整个后端。按新职责替换旧入口，删除已不再被调用的重复规则和转换层；不追加一层新 orchestrator 包住全部旧步骤。历史产物保留可读，不自动改变正在运行的冻结故事。新模式或新工作流的采用产生显式新版本，不能把已采纳的诺拉路线自动改回来源人物。

H5 的现行 V4 / `novel-h5-import.v1` / `ready`、EPUB 正文与章节映射、PNG/JPEG、大小与 spine 限制继续由代码严格执行。Genre/Tags 延用已实现的动态分类升级合同及既有交接手册，不在本轮文学重构里另造一版发行协议。私人来源分析、提示词与内部设计台账不进入公开包；故事中的秘密按批准的正文揭示。

## 10. 验收方法

先验工程，再验故事，再验正文。不能拿单元测试通过证明小说更好。

1. **模式回归**：原故事推演继承人物、关系、最后事件与已埋线索；新提案不冒充原文；改编变更只在明确范围内生效。用原创夹具覆盖原创、续推、重写及来源歧义。
2. **产物贯通**：作者采用的场面、关系变化和回报能在骨架与章卡追踪，导出不能偷偷重写；坏状态数据保留可读回复，不丢弃整轮创作，也不把未校验部分宣称完成。
3. **自由度回归**：甜感、幽默、悬疑、配角高光、静场及关系余波不会因不含怒／怜／悔而失败；事实冲突仍被发现。防止把家庭背叛套路固定成通用方法。
4. **协议与恢复**：部分返回、格式失败、超时、刷新、取消、同一任务重试不重复收费启动、不覆盖已批准数据；有问题可定位到具体阶段。
5. **小样本文学比较**：相同输入、同一模型与参数、相近输出预算，比较旧新首轮整体提案及一个故事段落。固定模型才能评估工作流，不同时换模型后归因于提示词。
6. **正文比较**：先选开篇、关系／反击高光、阶段回报各一类场面，写成实际章节再比较。重点看是否想读下去、人物声音、场景兑现、题材体验和重复解释；不能只看章纲的“爽点”字段。通过后再跑一本完整验收书。
7. **工程指标**：分别记录请求体量、首个可见输出、总用时、调用次数、格式失败、语义修订次数和成本。文学比较记录具体片段与作者选择，不编造“爽感提高百分之多少”。

这不是恢复付费的逐章 M3 评议功能。真实模型实验在后续开发验收时明确范围与用量后执行；本次未调用。

## 11. 提效复核与方案选择

这是一份可落地的推荐设计，还不能称为已经验证的最优方案。优化目标是在作者可接受的文学质量、连续性与产物正确性下，减少等待、调用和维护成本；不是追求调用最少，或保证模型每次都能写出畅销作品。

### 11.1 按优先级减少真正的工作量

| 优先级 | 调整 | 不牺牲什么 | 如何验收 |
| --- | --- | --- | --- |
| 1 | 已确认章卡直接进入写作；骨架、地图与交接由同一份设计生成，删除重复规划与语义重写。 | 已采用场面、人物决定和故事全貌。 | 追踪采用内容到实际请求及产物；统计被取消的重复阶段。 |
| 2 | 每轮一次讨论请求，同时给出具体故事提案与紧凑的状态变更；未变化的整张地图不要求模型重写。 | 作者决定、未决重大问题与真实阶段进度。 | 基于原版本合并更新，引用／状态错误保留完整可读回复但不覆盖正式状态；不增加一轮独立总结调用。 |
| 3 | 骨架纯组装与发行信息由代码完成；只对缺少的故事设计发起调用。 | 章节完整性、单章预算和正式交付合同。 | 已完成设计的导出阶段不再调用模型；缺少语义设计时明确显示待补内容。 |
| 4 | 正文改为写作＋联合审稿；必要问题才修订、复核。 | 每章仍接受独立于写手请求的内容审稿。 | 比较缺陷漏检、无必要修订和最终章节体验，不只数调用。 |
| 5 | 保存完整档案，按阶段装配当前决定、相关原文和状态；复用未变化的来源分析及检查点。 | 来源范围、未回收伏笔及关键原文可追溯。 | 输入清单显示选入／未选入范围；相关依赖变化使缓存失效，不能复用旧结论。 |

机械验证、版本管理与类型资料加载优先使用代码，不交给另一个模型“再确认”。人物、剧情和正文的依赖存在先后关系，不默认并行写多章后再花更大成本修复连续性。

篇幅较短时可以一次交付完整章卡；长篇先确定全局路线、结局和关键回报，再分段展开详细章卡。两种颗粒度保存在同一故事数据中；未展开的部分不能冒充可直接开写的完整骨架。每次请求聚焦一个有完整意义的故事段落，不为了省请求把全书塞进超大输出，也不机械拆成每章一次规划。

不默认降低用户设置的模型推理档位。先减少多余调用、重复输入和无意义长输出，之后用同一任务的数据判断是否值得按阶段调整档位。单纯把提示词缩短多少字，不能证明等待时间会同比下降。

### 11.2 等待体验和实际提速分别处理

请求开始就显示本轮要完成的故事段落、实际执行阶段、已用时间和最后收到内容的时间。支持流式正文的接入显示可读提案；尚未解析完成时标为草稿，不把片段当已采用决定。没有内容更新时如实显示等待，不能将后台心跳称为模型持续思考或虚构百分比。

任务在后台持久运行，关闭页面不会丢失；完成一个可恢复步骤即保存。返回页面恢复同一任务，格式问题只影响对应结构提交，不丢弃已收到的故事文本。减少重复重跑可以减少总耗时，但这些状态展示本身不会让模型推理加速。

### 11.3 为什么选联合审稿，而不是追求最少调用

| 方案 | 普通章预定应用级调用 | 优点 | 主要代价／风险 | 当前定位 |
| --- | --- | --- | --- | --- |
| 固定写作→编辑→核验 | 3 次 | 职责明确，修改后有独立检查。 | 好章节也被重写；额外长输出、串行等待，可能磨掉声音。 | 上一版提案，保留为对照。 |
| 写作→联合审稿→必要时修订 | 通过章 2 次；修订章额外计入修订与复核 | 每章有审稿，保留成立正文，避免无条件重写。 | 合并判断可能漏项；失败章并不一定比三阶段更省。 | 本次推荐，必须比较后验证。 |
| 写作兼自检→直接保存 | 1 次 | 路径最短。 | 写手可能重复自己的盲点，缺少独立审稿。 | 暂不作为质量优先的默认。 |

以上是拟议流程计数，不是当前实测，也不等于相同比例的耗时或 token 降幅。若第三次调用能稳定带来作者认可的明显提升，应保留在需要它的阶段；若联合审稿频繁要求无必要修改，先修审稿标准而不是增加更多审核层。

对照实验记录初稿质量、审稿发现、修改前后片段、总调用／时间／成本和作者盲选结果。不同题材至少包含不同情绪目标的样本；不能只在家庭背叛一本书有效就宣布适用于所有类型。对同一设计可重复少量样本，区分模型随机性。评价以具体文本和作者反馈为主，不使用模型自评分证明“最优”。

## 12. Gemini 审查记录，暂不实施

用户确认 PDF 来自“4 Argon Hight”。官方确认模型 ID 为 `gemini-4-argon`，可配置 `HIGH`；网页产品与 API 的上下文和系统指令不一定相同，不能保证仅切换型号就复制 PDF 效果。[官方入门](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/start/get-started-with-gemini-4)

现有 `core/llm_client.py:1041` 已有 Google SDK 文本调用和用量记录，通用 HTTP 层也有本地取消／超时。当前容器的 `google-genai` 为 2.34.0，已超过官方入门所列的 2.30.1 下限，不能误报必须先升级 SDK 才能开始适配。

但设置连接模板没有 Gemini，图片输入能力声明不含 Gemini，原生调用没有传入 thinking 配置，也没有流式内容诊断和结构化响应 schema；默认型号仍是已退役的 `gemini-2.0-flash`。[官方模型生命周期](https://ai.google.dev/gemini-api/docs/deprecations)

后续正式接入需覆盖连接／认证、模型目录、按阶段路由、能力与推理参数映射、输出上限、结束原因、流式观察、取消与重试、用量口径及离线契约测试。Argon 使用 LOW/MEDIUM/HIGH，不能直接发送当前所有 provider 共用的 max/ultra；总输出预算还要容纳思考，遇到截断或续传不能把空正文当成功。具体以目标接入端的能力为准。[Argon 开发指南](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/guides/gemini-4-argon)

按用户最新指示：先修正系统设计，Gemini 接入和任何单书重写均延后。

## 13. 开发顺序建议

1. 确认本设计中的创作模式、四字段提案、唯一骨架和文学／工程检查边界。
2. 先完成来源继承与头脑风暴新产物，实现一次端到端提案小样本比较。
3. 替换骨架交付与正文工作流，完成关键章节比较和恢复测试。
4. 完整创作验收与 H5 包回归。质量不足时按实际段落定位，避免再追加一层通用审核。

主要工作流已按本方案实现。真实模型下的文学质量、等待时间和费用仍需同输入对照验收；工程通过不证明提高付费率。长篇分段展开章卡及将每轮讨论直接维护为完整结构化章卡库，仍是后续深化项；当前交付先用两次语义整理生成已确认路线的全局设计与完整章卡，再由代码组装。
