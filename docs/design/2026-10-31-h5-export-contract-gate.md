## 2. 必须由代码保证的交付合同

### 新书与正文

1. 新小说只能交付 `package-manifest.json.schema_version = 4`、sidecar `schema_version = novel-h5-import.v1`、`status = ready` 的包。
2. 正文唯一来源是一个完整 EPUB，内含显式 `novel-epub-map.v1`。外部 Markdown、PDF、DOCX、旧 publication package 的章节不得被当作替代正文。
3. 正文来自已采用的权威版本；空稿、缺章、候选稿、过期编译结果不能静默回退。逐章核对正文、映射、预期章表和当前源版本。
4. EPUB spine 全部条目必须被映射：只能是连续正文，或一篇位于最前面的 Introduction 加连续正文。不得插入卷扉页、后记或其他非正文 spine 类型。
5. Introduction 不占正文章号、章节计费或免费章配额。有 Introduction 时最多 511 个正文章；没有时最多 512 个。EPUB 文件条目上限仍需独立满足，不能仅凭章数判定可用。
6. `number` 是一基的全书正文章号；`spine_index` 为零基 EPUB 序号；H5 `SourceIndex = spine_index + 1`。不使用标题或“第几卷第几章”猜测匹配。核对 OPF item ID、href、spine 次序、kind、XHTML 字节数及摘要。

### 身份、作者、分类与分卷

| 项目 | 代码责任 |
| --- | --- |
| 书籍身份 | 读取持久化 `project_instance_id` 生成 `book_id`；重编译、换封面和移动目录不新建身份；新书才创建新身份 |
| 章节身份 | 稳定绑定同书全局章号；中间插章、重排、拆章须显式迁移方案，不能悄悄改变已有权益对应 |
| 作者 | 读取已持久化作者字段，同步 sidecar、manifest 和 EPUB；打包阶段不调用模型取名；空值/旧字段缺失按已有存在性语义处理 |
| 分类 | 新书使用 `novel-classification.v1` 与 `novel-types.2026-10`；按维度验证 ID、数量、枚举及保序去重并集，复算语义身份；不接受模型自造 ID |
| 分类一致性 | EPUB 内嵌分类、独立分类 JSON、sidecar/manifest 引用和存在的 publication package 必须同源一致；不能只改 catalog 字符串 |
| 结构与分卷 | 使用 `narrative-format.v1`、`novel-serialization.v1`；正文范围连续、无重叠、无遗漏，每章恰归一卷；卷内章号由代码计算 |
| 系列 | 分册有独立 book_id；series_id 只用于关联。系列及分卷不自动改变免费窗口、计费、历史解锁权益 |
| 同步更新 | 分类、卷名、作者、Introduction、封面各自复算受影响组件及聚合摘要；只有正文变化才改变相应正文版本，不把包版本当书籍身份 |

模型可建议题材分类和创作内容，代码必须验证后再接受。无明确合法映射时返回待处理问题，不能隐式归为 `other`、丢弃未知 ID 或自动改目标字典。历史 `2026-09` 仍按原版本验证；需要升级时走显式全链重编译，保留原包证据。

### 封面

- 仅接受真实解码成功的 PNG/JPEG，核对字节、MIME、扩展名、尺寸、像素数、候选身份和选择关系。
- 已选封面用独立 selected 文件；不能被同名 pending 文件覆盖。候选顺序与稳定 candidate_id 分开。
- 未选择时不替用户选择，不以模型质量分或人工接受理由控制选择。只有候选时保持 H5 既有封面；缺失可选组件不等于删除。
- WebP 原始资产可以保留在项目内，不能原样装入 H5 封面角色。若实现派生 PNG/JPEG，使用固定编码配置、保留原图及派生关系，所有包内候选引用、选择关系、摘要同步；转换失败即阻断导出，不能假冒格式。
- 超过 24 候选时要求明确交付候选集合，保留项目内所有历史；不得悄悄省略当前选中封面或生成无效候选引用。默认当前批次加有效已选封面的具体投影规则需代码和测试锁定。

## 3. 资源限制：独立计数，全部强制

所有 MiB 均为 `1024 * 1024` 字节；等于上限可接受，超过上限必须失败。以下取自目标实际源码，不能只写提示词。

| 层级 | 上限 |
| --- | --- |
| 外层 ZIP 压缩字节 | 64 MiB = 67,108,864 bytes |
| 外层 ZIP 解压累计 / 条目 | 128 MiB / 1,024 |
| 内层 EPUB 压缩字节 | 16 MiB = 16,777,216 bytes |
| 内层 EPUB 解压累计 / 条目 | 32 MiB / 600 |
| EPUB spine | 512，包含 Introduction |
| 单 JSON / 单源 XHTML | 各 4 MiB |
| JSON / XML 嵌套深度 | 64 / 128 |
| 单封面字节 | 8 MiB |
| 单封面宽、高 | 各不超过 8,192 px |
| 单封面总像素 | `width * height <= 16 * 1024 * 1024`（16,777,216；README 简称 16 million） |
| 候选封面数 | 24 |

章数和允许非正文类型在规划前预检；写作中的预计字节仅用于预警，最终仍以生成后的真实 bytes、解压计数与图片解码为准。不能让模型估算充当验收。

大小超限允许通过确定性的无内容损失措施解决，例如 EPUB/ZIP 无损压缩、按明确导出规则减少非必需附件。不得截断正文、删除章节或悄悄改变书籍/分册身份以通过校验；需要拆书或有损图片调整时展示具体方案并按用户已有授权执行。外层和内层限制分别检查，不能把 EPUB 拆成两个文件绕过“唯一正文 EPUB”规则。

路径与解析同时拒绝：绝对路径、越界路径、重复路径、符号链接、加密成员、DTD、无效 UTF-8 元数据、重复 JSON 键、不明确的角色或引用。读取时计数和 CRC 校验，防止 ZIP 头声明大小与实际不一致；不先无限解压再检查。

## 4. 编译顺序与失败边界

```text
冻结已采用正文、元数据、封面选择及 target profile
  → 本地预检（来源、章表、身份、分类、分卷、容量）
  → 代码构造出版 DTO / XHTML / OPF / EPUB map
  → 在临时快照编译 EPUB、允许的附件和元数据
  → 由实际最终 bytes 计算组件摘要、sidecar、manifest
  → 临时 ZIP 完整反读校验（与 H5 相同接受条件）
  → 再核对源版本与 profile 未变
  → 原子发布已验证快照、ZIP 和验证回执
  → 各页面下载同一个已验证包
```

打包服务是本地确定性操作，不调用 LLM，不请求模型修 JSON/hash。模型输出仅能进入经过类型检查的内容输入；不能直接作为 OPF、spine、归档路径、ID 或签名字段使用。

复用现有 delivery lock、安全文件读取、编译器与 `core/h5_acceptance.py`，将目标 profile 的纯校验集中到一个公共边界；避免再造互相矛盾的 UI、API、CLI 校验器。预检用于早反馈，最终 ZIP 反读用于验证实际字节，两者目的不同，不得只调用同一个生成器自证。

正式 ZIP 原子替换前必须成功；验证报告在外部保存，绑定 ZIP 原始 SHA-256、源快照 SHA-256、target profile ID、字典 SHA-256、校验器版本和检查结果，不把报告自身放进需要自我哈希的清单。缓存只有全部绑定相同才复用。

并发封面选择/改稿后，旧检查不能批准新包；源变更则本次产物标记过期，不发布为当前。校验失败保留旧包及候选临时证据，不覆盖已验证版本。旧包可作为明确标注的历史版本下载，不能假称为最新。

UI 统一显示“准备交付 / 校验中 / 可下载 / 需处理”，失败包含路径、实际值、期望值、原因码和本地修复动作。作品库、详情与封面工作室共用同一下载服务和状态；只读列表不触发重打包或模型调用。修好本地合同问题后可以重试打包，不重写小说、不重新出图、不增加模型费用。

## 5. 字节、组件和聚合摘要

- 文件 SHA-256 对最终原始 bytes 计算，输出小写 64 位十六进制；不能先 trim、换行归一或重新 stringify 后校验旧摘要。
- XHTML 摘要对 EPUB 内该成员原字节计算；Markdown 摘要不能用来校验 XHTML。
- 新组件/修订摘要的 canonical JSON 使用 UTF-8、键排序、无多余空格及结尾 LF、保留 Unicode 和数组顺序；不引入浮点值。历史 serialization 语义身份已有有限浮点字段，保留既有算法并用跨语言夹具验证，不一刀切改哈希。
- 正文、Introduction、作者、分类、serialization、选中封面、封面元数据、发布文案按既有合同各算版本；再计算 `import_revision_sha256`。
- `manifest.files` 路径升序，精确列出除 manifest 自身之外的全部归档文件及实际 size、media_type、SHA-256、role；最终计算 `package_revision_sha256`。禁止缺项、额外未声明成员、自包含哈希。
- 同一输入快照的发布 DTO 与相关摘要必须稳定；归档排序、时间戳和编码策略固定，避免重打包仅因当前时间产生无意义新版本。身份与用户内容不为追求稳定性而重写。

## 6. 开发模块与验收

首批工作落在现有模块上，具体拆分以保持单一职责为准：

| 接入点 | 计划 |
| --- | --- |
| `core/h5_acceptance.py` 及拟议 target profile | 固定目标限制/字典指纹；提取可复用纯字节校验；保留外部业务回执职责 |
| `core/h5_import.py`、现有 EPUB compiler | 全量章节映射、前言、作者、同源分类/结构校验与确定性编译 |
| `core/delivery_package.py` | 快照编译、真实 ZIP 校验后原子发布；禁止未验证产物标记 ready |
| `core/cover_delivery.py` | 仅使用已验证包；精确区分封面选用状态与交付同步状态 |
| delivery summary / API / CLI | 共用 target profile、同一验证回执、清晰错误和本地重试；不暴露模型自由拼装包的入口 |
| 现有 tests / H5 acceptance fixtures | 补齐资源边界、坏包和跨语言契约；不引入重复协议实现 |

必须有三层验证：

1. **本地确定性验证**：对程序生成的临时 ZIP 全量反读，结构、正文、分类、媒体、资源及摘要均通过。
2. **目标解析器契约验证**：使用冻结版本的真实 Go `zipimport.Parse` 对新生成技术样包运行验收；不连接业务数据库、不联网或调用模型。CI 使用可复现的源码/测试工具来源及指纹，不依赖开发者电脑的绝对路径。模型替身或 Python 生成器自检不能代替该层。
3. **业务导入验收**：测试环境确认新建、重复导入、封面/分类/卷名独立更新，书章身份、阅读进度和已解锁权益保留；保留绑定具体 ZIP 的回执。Parse 通过不能宣称业务导入及权益已验证。

## 7. 与总体方案的关系及执行顺序

**M0 必须先完成目标契约基线、上述差异修复与确定性导出门，再放行新质量优化产物用于正式 H5 交付。** 后续 M1–M5 的生成、修订和选封面不能绕过此门；关闭文学评议功能也不能关闭交付校验。

文学质量靠设计、正文、评议及读者验证改善；本合同保证的是可验证的产物正确性、身份稳定性和资源合规。一个故事有审美争议仍可正常导出；一个小说评分再高但 EPUB 缺章或分类非法，也必须阻断导出。

本次仅更新方案、修正文档，并按用户指示保存当前本地开发基线、合并至 `stable/baseline-65e1195`、从该基线创建 `codex/novel-quality-optimization`。不启动模型实验、不部署、不修改 H5 仓库，不把方案描述当作已实现功能。
