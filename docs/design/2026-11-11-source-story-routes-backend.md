# 资料理解、整书路线与头脑风暴交接：后端实现方案

状态：**已批准并实现，工程回归完成；未部署。** 2026-11-11；工作分支 `codex/long-form-planning`。下文保留设计依据，最终模块和验收结果见[实现报告](../reports/2026-11-11-source-story-routes.md)。本次不部署、不重启、不重新分析真实资料、不修改运行中任务。

整体评审入口见[方案总览](2026-11-11-source-story-routes-review.md)。

## 1. 目标与交付语义

资料分析应帮助作者选择“这份素材可以发展成哪一部完整故事”。一次来源理解产出共同的已知来源进度，以及默认三条、可配置为两条的整书路线。每条路线必须从本次创作模式的共同起点走到高潮和结局，说明因果、关系变化、读者期待与情绪兑现。路线不是逐章提纲，路线卡不是原资料某一章的独立续写。

沿用 `core/creation_mode.py` 的三个模式：`source_development` 从原文最后已知节点推演；`original_rewrite` 遵循作者明确的保留与改写范围，不强制承接最后一句；`reference_creation` 借鉴叙事机制，独立设计人物、因果与结局。三者都完整理解资料，但不能对借鉴创作施加续作的原书伏笔继承义务。共同起点的含义随模式绑定，来源本身的事实与终点不被改写。

作者选择路线后进入现有 Workshop 深化。选择确认的是讨论方向，模型提议的场景、秘密、具体反转仍可修改，未来事件不能因此进入已发生事实。只有作者明确触发“生成完整骨架”，才执行已有骨架交付流程；正文创作仍沿用现有启动动作。

“只提供六章免费内容”是正常的来源范围：原作后续未知，正是新的续写设计空间，不是等待补齐整部原作的错误。必须区分没有提供的后文与提供了却尚未读完的正文；只有后者影响本轮阅读完成状态。

实现同时覆盖资料库入口、Workshop 内选资料入口和历史分析新增路线入口。统一模块负责资料完整性、路线生成、版本读取与选择交接，前端不得自行拼一段长文本代替结构化交接。

“Workshop 内选资料”包含**新建头脑风暴表单中直接上传现有作品**：先在当前草稿内完成整书路线选择，再进入共创；已有构想、频道、Genre、Tags 和补充要求是设计输入，不因导入而清空。作者还可以提交修正/补充意见，修订指定路线、重新核对来源理解或增加其他整书方向。这些动作共享同一后端合同，不能只在资料库页面提供。

## 3. 模块及职责

外部调用者只使用 `SourceStoryDesign` 的准备、执行/恢复、读取版本、选择交接接口。实现可分文件，但不让入口分别承担容量估算、提示词拼装和迁移规则。

| 模块（拟新增或扩展） | 职责 | 不负责 |
|---|---|---|
| `core/source_story_design.py` | 统一准备/执行/恢复，阶段依赖与公开结果 | 操作正式小说状态或主动启动正文 |
| `core/source_evidence.py` | 完整来源索引、证据台账、共同终点、覆盖回执、原文取回 | 用规则推断剧情事实或合并不明人物身份 |
| `core/source_routes.py` | 路线数据合同、生成任务、引用验证、推荐理由与比较投影 | 接受模型自发“作者已批准” |
| `core/source_design_store.py` | 不可变产物、运行清单、请求回执、原子状态转换、幂等操作 | 以可变 latest 指针作为历史身份 |
| `api/source_routes.py` | HTTP 参数、权限/路径校验、调用统一模块 | 自己生成路线或自动迁移旧小说 |
| `api/workshop_source_handoff.py` | 选择回执、创建讨论与首轮关联、来源/知识冻结 | 把模型路线全文写成作者原话 |
| 现有 SourceLibrary / SourceVersions / CreativeTypeStore / Workshop | 来源文件、历史读取、知识版本与后续共创 | 因增加路线而修改旧回执身份 |

依赖以构造参数传入：来源仓库、模型请求执行器、容量适配器、类型目录、时钟及取消信号。业务接口测试可使用同样接口下的临时仓库和模型替身。继续使用现有单机文件存储/原子写和任务 runner，不引入消息中间件或分布式服务。

## 4. 领域对象与不可变身份

### 4.1 来源理解版本 `source-understanding.v1`

每个版本包含：

- `source_id / source_sha256 / parent_analysis_sha256?`：确切来源与可选旧分析父版本。
- `source_index`：每个文件的类型（Synopsis、正文、补充资料等）、叙事单元、顺序、完整文本 SHA、长度；每个分段的文件 ID、字符起止、片段 SHA。
- `reading_receipts`：每段发送、完整接收、成功解析的请求身份；分段拼接必须逐字符等于原文件。
- `evidence_ledger`：追加式命题集合。命题保存代码分配的 ID、原文位置、事实类别、解释、实体/线索链接和不确定性。模型使用预置片段 ID，代码校验位置，不要求模型抄长引用。
- `narrative_endpoint`：唯一正文终点、最后事件、人物/关系状态及知情边界。Synopsis 和补充预告不能推进终点。
- `open_threads / unresolved_evidence`：开放线索及相互冲突/不确定的观察引用。不能因后续摘要未提到而删除。
- `opening_analysis`：基于完整来源理解的开局代入与张力机制解释，引用相关场面及观察；描述人物欲望/恐惧、信息差、权力关系和可延续/改进的抓手。这是模型编辑判断，与客观事件分开，不宣称有真实读者留存测量。中间阅读批次允许尚未形成，完整理解产物再汇合。
- `summary_projection`：供阅读的概述。它是可重建视图，不是设计唯一依据。
- `coverage`：按原文范围、台账命题和未决事项分别记录完成状态。

所有来源身份、SHA、片段/命题/路线 ID 由代码分配或计算。模型只选择预置证据 ID 并返回判断/设计，不计算哈希，也不以“准确复述一长串哈希”作为成功条件。模型新增的命题用本次局部序号，验证后由代码赋予持久 ID。

完整输入的一次调用尚无事实台账时，模型引用请求中已由代码分配的 `source_span_ids`。同一回复可以用局部命题序号连接路线与新提取的命题；代码验证原文引用和序号后统一生成持久 evidence ID。后续阶段才直接引用这些持久 ID，不能要求第一次调用凭空引用尚未存在的台账。

命题类型至少分开 `observed_event`、`character_statement`、`synopsis_promise`、`uncertain_inference`。人物说谎的台词不直接等同于世界事实；模型后来提出的新秘密不写入事实台账。

不设置会丢项的“最多 30 个事实/最多 N 条未决线索”。较大的集合分页/分片保存，使用内容哈希和根清单证明完整性。集合里的等价关系可以引用原项，不删除原项；冲突不以“最后一条覆盖”解决。

### 4.2 路线集 `source-route-set.v1`

路线集绑定 `understanding_sha256`、来源/分析版本、创作模式、作者已有要求、类型目录版本、设计协议和真实请求出处。路线 ID 由代码分配，绑定该版本；同一路线修订产生新内容版本，不能仅改标题后沿用错误身份。

推荐只存在一个 `recommended_route_id`，附简短故事理由，不输出“成功率”“留存率”“爆款分数”。默认请求三条路线，作者可以明确要求两条。请求三条而只完成两条时可展示“已完成 2/3”，但不能静默标为全部完成；不为凑数伪造同义方案。

单条路线的主要数据：

| 字段组 | 内容和约束 |
|---|---|
| 识别与选择 | `route_id`、名称、一句话吸引点、与其他路线的实质区别 |
| 承接 | 共同终点引用；继承的重要事实/开放线索；适用叙事单元 |
| 完整因果线 | 具体进入故事的第一幕、目标与压力、第一步行动及代入机制；欲望/阻碍、重要选择和代价、升级、转折、高潮具体破局手段、明确结局与余波；阶段数量自由，不绑定章节数 |
| 人物关系弧 | 谁希望得到什么、害怕失去什么、误解/欲望如何改变行动、权力/依附或对抗关系如何变动、最终状态；不以通用“成长”替代故事 |
| 读者情绪设计 | 读者在意谁/什么，具体事件唤起什么期待，何时加压/反转/释放，最终得到何种情绪回报；叙述自由，不使用强制情绪枚举或数值曲线 |
| 核心看点 | 候选关键场面：参与者、冲突、选择、可见变化及读者价值；必须与主线相连 |
| 长线吸引与兑现 | 悬念/关系期待/欲望承诺，如何维持和变形、在哪里兑现或有意留下余韵；支持非悬疑和安静场景，不强制每段悬崖结尾 |
| 类型推荐 | 一个 Genre、1–2 个 Tags、读者频道建议、每项与具体冲突/关系/情绪回报的对应理由 |
| 待定设计 | 新增假设、重要取舍、若采用将改变原人物/核心关系的明确说明 |

例如“受辱→打脸→爽”不构成有效情绪设计。需要说明“谁在何种场景被否定、为何这件事伤害其所珍惜之物、如何付出代价取回主动权、读者最终看到什么得到兑现”。要求创作具体性，但不能用情绪词出现次数自动判通过。

创作提示采用作者提供的商业主编版，全文与适用范围见[提示词评审稿](2026-11-11-source-story-routes-prompts.md)。高张力、关键选择及情绪兑现进入正常设计输出，不新增“情绪 Agent”或固定付费终审。生死局势、暗黑共犯等是例子，不作为每部书的必备语义校验；不得将文学指导转成低通过率的机械门槛。来源开局解释和新路线第一幕共享同一次正常理解/生成，容量足够时不增加调用。

原文所有开放线索不必在卡片上逐条展开。内部需保留每条线索的 `carried / resolved_by_proposal / intentionally_open / out_of_scope_with_reason` 处置及证据引用；“忽略”不能成为默认处理。候选结局是新增提案，不声称是未读原作结局。

`out_of_scope_with_reason` 仅用于有来源标记的其他短篇/非正文材料，或作者明确选择的创作范围。不能由模型给一条重要伏笔编理由后排除；所选故事的核心承诺必须有设计去向，仍留开放的承诺也要明确说明。

### 4.3 类型推荐与作者最终选择

推荐使用真实启用目录中的稳定 ID，目录快照包括名称、类型、可供选择的说明及版本身份。不得发明当前库不存在的 Genre/Tag，不按原书平台标签机械复制。

新生成合同不复用旧 `PLANNING_RULES` 中固定的 female-oriented 前提。已有作者频道按作者选择；未选择时给出有故事依据、可修改的频道建议，不因建议改变来源人物身份。旧已发请求仍保留其原始提示和出处。

推荐阶段传入完整可选目录；目录用于识别选项，不用自动压缩后的指南代替作者知识全文。只有选中的完整知识版本进入 Workshop 的正常知识编译流程。必要时模型可以依据目录引用读取相关原始指南；不得声称未读指南的写法已经得到完整执行。

推荐记录和作者最终选择分别保存。作者可以改变频道、Genre 和 Tags；新选择作为下一轮设计约束，不静默恢复模型推荐。更换后先由 Workshop 解释故事、情绪和看点应怎样适配，不自动更换主角性别或重写原文事实。

进入讨论后再次修改类型，沿用既有设定更新流程，创建新的 session input / 类型快照 revision。原始推荐与最初选择回执保留历史身份；后续编译采用作者最新有效选择，不能从路线交接回执把旧标签覆盖回来。类型改变也不自动采用新剧情。

进入讨论前重新验证类型版本是否存在。被停用/删除时保留路线和旧推荐，界面只要求替换不可用选择；不能为了标签变化重新读取来源。已经创建的讨论沿用其冻结版本。

### 4.4 路线选择回执 `source-route-selection.v1`

包含 `operation_id`、来源/分析/理解/路线集身份、路线 ID/内容 SHA、作者最终频道与 TypeRefs、原样补充意见、创作模式、选择时间及生成的 session ID。

**选中路线不是把模型输出升级为作者原文。** 路线全文存在 `selected_proposal` 中；作者点击形成独立的选择事件，作者自行填写的补充意见保存为精确作者文本。原作者事实、模型假设、路线选择、细节确认保持不同来源。

界面可以预览完整路线，但不能把自动填充的路线全文作为 `premise` 或用户消息提交并标成全部已确认。现有故事地图的 settled 证据需要扩展为可核验的 `author_action_ref`：它能证明方向被选中，不能证明所有场景已批准。旧消息/输入证据规则不变。

新交接入口允许 `source_route_selection` 加可选 `author_note` 创建讨论，免去用户重新填 `premise`；现有普通新建入口保留原校验。初始化时由代码根据选择回执把 `direction` 记录为已选讨论方向，`opening/middle/climax/ending` 的具体设计仍为 proposed，除非作者后来明确确认。模型不能通过返回 settled 自行升级这些区域。

### 4.5 作者上下文、反馈与路线修订

路线生成接收 `author_context`：已填写的原样构想、补充要求、创作模式、输出语言/篇幅要求，以及当前有效的频道/Genre/Tags 选择。每项保存来源与版本；缺省 UI 值不能伪装成作者明确决定。非空的作者实际选择优先于模型推荐；推荐可以附替代建议，但不能直接替换现有选择。草稿导入、资料库与历史路线入口使用同一语义，不另设“导入版”提示词。

每次反馈作为追加记录保存 `feedback_id`、`exact_text`、`base_route_set_sha256`、指定路线版本、提交时作者上下文和顺序。原话保持完整，另存用于执行的作用域解释；不能用模型提炼的两句话替换作者原提示。后续请求携带完整有效要求及其出处，最新明确要求只取代同一范围内冲突的旧要求，兼容要求继续有效；被取代的原文及关系保留，不能以 latest 一键删除过去所有约束。

| `task.operation` | 作者含义 | 产物与边界 |
|---|---|---|
| `initial_routes` | 根据全部资料首次提出整书方向 | 默认 3 条有实质差异的路线；遵循既有作者上下文 |
| `revisit_source` | “你把第二章的关系理解错了，重新看这段” | 重读实际相关原文/依赖，追加解释修订与新理解版本；不可改写原文件或把作者意见伪装成原文引证 |
| `revise_routes` | “保留 B 的结局，女主的选择再主动一些” | 只修订指定路线及必要关联节点，保留旧版本、继承未受影响内容与完整因果/情绪弧 |
| `expand_routes` | “再给我两个更有情绪张力的方向” | 在现有候选之外追加完整路线，不覆盖旧候选；默认新增 2 条，作者明确数量优先 |

以上数量是单次请求/页面目标，不是历史候选总量上限。更多路线必须在人物选择、关系终局、冲突解决或情绪兑现上有实质变化，不能只换标题或局部场景。新增候选仍必须遵循该模式的共同起点并走到完整结局；原故事推演必须承接全部资料的最后已知节点。

作者可以通过 UI 指定操作，也可以自然语言同时要求“修订 B，并再给两个新方向”。服务保存一个主 `task.operation` 和有序 `requested_actions`，将同次复合请求的依赖串联起来；界面模式不能压过明确原话。普通偏好无需反复确认，只有无法兼容且会改变作者核心取舍的歧义才询问。动作分类不另加固定付费轮次，可在生成响应中同时解释执行范围，宿主只接受请求所授权的操作。

必须区分三种反馈：**资料理解纠正**要核对原文；**作者新增设定/改编决定**是独立作者要求，可以授权改变故事但不改旧原文；**偏好/候选评价**只影响设计。`revisit_source` 的解释修正（clarify source interpretation）保存原命题与新解释之间的 supersedes/争议关系，不把整份来源账本直接覆盖。无法证实的意见保留出处和不确定性，不能自动升级成 observed_event。

每份路线新版本保存父版本、触发反馈、改变的因果/情绪/看点节点与理由。未改的旧路线通过不可变版本引用保留；受新要求影响的旧候选显示“按旧要求生成/需更新”，不因仍可阅读就假称符合最新意见。已选路线不跟随 latest 偷换：作者可明确选择旧版本的方向并进入讨论，系统说明差异且完整携带最新要求，由首轮协调仍为 proposed 的细节；不能静默恢复旧要求。只有核心作者取舍确实无法兼容时才澄清，不强制先返回资料页重跑。现有讨论和写作任务不因来源页追加反馈而改变。

## 5. 生成流程、容量与完整信息

### 5.1 优先走完整输入路径

构造完整请求后才判断容量，计入系统提示、全部原文、目录、身份/协议、已存在作者要求以及响应余量。使用连接真实声明的输入能力与当前配置；未知容量不能猜成一个很小的固定上限，更不能把传输字节限制当作模型 token 上限。

能够容纳时，一次读取完整来源并返回来源理解与路线集；内部结构和请求回执仍分开落盘。没有必须先调用“提案 Agent”、再调用“情绪 Agent”、再调用“全局审核 Agent”的固定流水线。容量足够的六章资料正常目标是 **一次创作模型调用**。

若完整输出较大，可把完整事实读取与路线生成拆为两次；只拆完整产物，不要求模型把内容缩短到丢失关键事项。显示文字折叠/摘要不改变底层保存内容。

### 5.2 分段路径：完整来源和台账不进入有损摘要链

当完整请求无法容纳：

1. 沿完整正文顺序规划分段，优先段落/场景边界；保存原文起止位置与完整覆盖清单。超长段落可按编码安全的范围切分，边界上下文显式标记，不能冒充完整场景。
2. 每段读取原文，生成有来源引用的命题、关系/知情变化及开放线索。所有结果追加保存；不反复以“30 条精简摘要”替换旧事实。
3. 按来源顺序整合共同终点与因果链接。每个台账分片都必须被处理；不能只取 top-K 命题或相似度最高的片段。跨段同一人物/线索通过稳定引用相连，歧义保留。
4. 在完整路线草案上逐批整合尚未处理的证据。每个请求含当前完整路线、当前完整证据单元及其必要的原文与关联证据；返回有引用的局部设计修订/明确无变更，更新覆盖回执。路线草案用于保持故事方向，不能替代事实台账。
5. 已有引用的远距离依赖、矛盾或重解释需要取回原始片段，不能只让模型凭摘要判断。候选改变时，根据被修改节点的证据和因果依赖使相关回执失效，重算受影响部分；不因任意变化全书重审。
6. 所有原文范围完成阅读、所有台账分片完成整合、所有候选影响项得到处理后，发布路线集。最终整合可在最后一批完成，不额外固定增加一轮“总审”。

证据整合以“一批来源 × 当前整组路线”处理，避免“每条路线 × 每一章”重复审查。只有单批无法装下全部路线时才拆路线内容，原始证据缓存不重复付费读取。分段之间有真正依赖的部分顺序执行；独立阅读可受控并行，但不在本次设计中承诺并行提速比例。

对局部取回的完整性限制：有索引的依赖不能因为相似度排名低被排除；没有命中的资料也不能视为已经检查。全量覆盖处理负责不遗漏范围，原文取回负责具体争议，不允许纯检索替代全量来源阅读。

原文留白、角色身份未知和多个兼容解释可以带入路线并继续设计。只有确切原文依据互不兼容且会改变作者必须决定的故事身份/保留范围时，才出现 `needs_author`；模型自己提出的假设冲突由模型修订，不转成作者阻断任务。

### 5.3 无法容纳必要证据时

优先拆分独立任务、输出分页及复用相同上下文；不能截掉早期章节、人物事实、未决线索、作者要求或 selected route 的结局。不能把来源文件转附件后未经能力验证就宣称模型读到了全部内容。

确有不可分割的关联证据集超过连接能力时，保存全部进度并清楚说明当前连接不足，允许换连接继续尚未完成阶段；不给作者技术对账表，不伪造“分析完成”。这属于明确能力不足，不应被包装成故事质量失败。

工程可保证原文与台账存储完整、请求范围可重建、已声明依赖未静默删减。模型仍可能漏理解某个细节，不能把哈希和覆盖回执表述为语义理解或文学质量的数学保证。验收需要跨段伏笔、远距离矛盾和人物知情变化的行为用例与真实内容 review。

未知容量不能当作无限容量。适配器提供的限制、配置的可信限制和上游明确拒绝应有不同出处；无法获知时保守拆分完整任务并保存实际请求大小，不宣布某模型“必定能完成任意长资料”。

### 5.4 候选变更后的覆盖闭合

证据处理回执绑定 `evidence_ids + route/node revision + request view SHA`，不是一个永久有效的“这段读过了”。模型只能修改请求授权的节点/字段，代码拒绝越界差异；节点新依赖必须进入依赖图并取回证据。

发布前，每个受影响的证据项都必须指向当前兼容的节点版本。改变人物身份、承接终点、核心关系、全书前提或结局等全局含义时，不能只保留旧局部回执；没有可验证影响范围的改动默认使该路线的相关来源覆盖失效，并进行更广的重新整合。新跨段依赖会向前回查，不能只往后遍历。

这套闭合证明的是“最新候选确实处理了应处理的证据”，不是机器能确定所有潜在文学含义。重大变化可能增加整合请求 M；不承诺 M 恒小，也不设置每条路线无条件再跑一次全文审稿。界面仍以已保存进展为准，避免把曾完成的覆盖误显示为当前版本已完成。

### 5.5 输出截断与格式问题分开

保存原始回复、可用的 `finish_reason`/结束状态、使用量与请求身份。上游明确因输出容量截断时，保留原响应，后续按完整产物或节点分页输出；不得让模型“再压缩一下”而删掉结局、情绪回报或原文事项。分页有明确清单和完成标记，所有页齐全且引用一致后发布。

只有完整回复的包装/字段协议错误才进入格式纠正路径。缺失结束状态不能仅靠补括号视为完整；收到残缺 JSON 与作者真实原文冲突是不同错误类别。

### 5.6 调用数量与效率口径

| 场景 | 正常付费步骤 | 不发生的调用 |
|---|---|---|
| 全部资料、目录和响应可完整容纳 | 1 次共同理解+整书路线；输出需分离时 2 次 | 不逐章独立续写，不逐路线再读一遍 |
| 已有完整新台账，仅重新设计路线 | 1 次；不足时按完整证据分片整合 | 不重新付费读取已完成且身份相符的事实阶段 |
| 旧分析升级，原文可完整容纳 | 1 次读取原文并生成路线，旧分析作为背景 | 不把旧摘要自动认证成完整台账 |
| 大资料分段 | N 次完整读取 + 必要整合请求 M；M 由真实容量和依赖决定 | 不使用固定 70 组核查，不自动乘以路线数 |
| 选择路线、改标签、创建讨论 | 选择/创建 0 次；正常首轮共创 1 次 | 不重新分析资料、不再生成同一组初始路线 |
| 协议失败 | 优先无语义变化解析；必要时对失败产物自动纠正一次 | 不重跑成功读取，不制造新的文学判决 |

这些是执行路径目标，不是固定调用成功保证。界面展示已完成步骤、实际调用及当前阶段；不显示未经实测的加速倍数。

### 5.7 继续分析与追加候选的复用边界

初次完整阅读完成后，修改“更强情绪拉扯”“不要复合结局”等设计偏好复用相同来源理解与完整证据，不重新付费读全书。`revisit_source` 根据指向的片段及关联命题重读，影响终点、身份或核心关系时扩大核对范围；解释修正发布新 understanding，而不是改变旧版本 SHA。依赖失效按第 5.4 节计算，不能因“缓存已读过”跳过受影响章节，也不能每次补一句偏好就从头开始。

`expand_routes` 需要比较既有方向的实质差异。候选较多时，宿主提供全部候选的比较清单与确切版本，按需逐批核对完整路线；不能只看最近三条就宣称新增方向从未出现。比较清单用于导航，不代替来源事实或已采用路线正文。新路线对全来源仍需完成对应整合；旧路线已经完成的阅读/请求不重复购买，旧候选保留在历史列表。

提示词正文、各操作块、证据输入边界和模型响应字段以[分析与路线提示词评审稿](2026-11-11-source-story-routes-prompts.md)为准。宿主按本次动作提供 `response_schema` 和可用局部槽位；模型返回局部内容与已有证据引用，不生成持久 ID、SHA、版本回执或虚假的作者批准。完整反馈原文、有效要求、候选版本和来源范围都计入真实容量，不通过裁剪早期意见适配小上下文。

## 6. 任务状态、请求回执与恢复

每个设计运行保存 `created → reading → integrating → designing → ready`。阶段可进入 `paused / retry_wait / pending_unknown / needs_capacity / needs_author / failed`；`needs_author` 仅适用上节的真实原文/保留范围选择，`pending_unknown` 表示已发送请求结果尚无法确认。可用旧路线与正在生成的新路线并存；新任务失败不能抹掉旧结果。GET 只读，不能生成、升级或修复。

每次外部请求按 `prepared → dispatched → response_received → parsed → applied` 记录。先保存原始响应及哈希，再解析，完整验证后才发布产物。错误回复保留。发生协议问题只针对失败产物进行纠正，保留已验证事实和路线；持续无进展时保留可恢复状态，不无限买相同结果。

网络错误依据已知结果处理：明确失败可按已有退避机制恢复；未知结果先检查同请求的已接收回执。既不能把未知当成功，也不能盲目重复购买。此能力需由统一请求执行器向来源模块提供，来源页面不要求用户填写请求编号和失败证据。

应用可以保证自己的产物/讨论/首轮操作幂等，不能在上游不支持幂等键或结果查询时保证供应商只计费一次。遇到“已发送但结果未知”，先保留并自动核对可用回执；没有可核对机制时显示请求未确认并保留工作，不编造已失败、已完成或零重复计费承诺。

运行锁按资料与设计运行隔离，取消信号按 run 隔离；付费请求返回后先落盘再结束取消，避免取消后丢掉已付费工作。跨资料无共用可变上下文。

模型配置是显式请求参数，不写 `os.environ`。每个已发请求冻结真实模型、连接、参数、容量及请求身份；运行级配置可以调整，尚未准备/发送的阶段使用新配置。已完成产物只要来源、协议和依赖仍匹配便保留，连同原模型出处；不能因换模型全部失效。已准备但未发出的旧请求应以明确新 attempt 重新准备，不能修改旧回执。历史已发请求不能悄悄改身份。

## 7. HTTP 接口与持久幂等

以下是拟定接口；最终字段名在实现前与前端合同固定。现有 `/analyze` 请求与旧载荷继续支持。

| 接口 | 作用 |
|---|---|
| `POST /api/source-books/{id}/route-runs` | 显式提交首次设计、继续修订、核对来源或追加路线；包含 operation_id、task.operation/requested_actions、可选 base_analysis_sha256、mode、原样作者反馈、作者上下文、目标数量和确切父路线版本。新资料不需要先存在旧分析版本 |
| `GET /api/source-books/{id}/route-runs/{run_id}` | 只读进度、可恢复动作、已完成版本及错误类型 |
| `POST .../route-runs/{run_id}/pause` | 暂停此设计运行，不影响分析旧版本或其他作品 |
| `POST .../route-runs/{run_id}/resume` | 按既有回执继续；可显式采用当前连接执行尚未完成部分 |
| `GET /api/source-books/{id}/route-sets` | 路线历史列表；绑定确切分析版本 |
| `GET .../route-sets/{sha}` | 读取完整不可变路线集与可用性说明 |
| `POST /api/workshop/source-route-handoffs` | 保存作者选择，创建或按版本绑定尚未开始共创的当前草稿/讨论，关联正常首轮；返回 session_id、operation_id 和真实首轮状态 |
| `GET /api/workshop/source-route-handoffs/{operation_id}` | 恢复浏览器重试或服务崩溃后的交接状态 |

创建/选择都使用持久 `operation_id + canonical payload SHA`。同 ID 同载荷返回同一运行/讨论；同 ID 不同载荷返回冲突且不修改旧操作。JobRunner 的内存 unique_key 只作进程内快捷去重，不能作为唯一正确性依据。

操作身份按 workspace 限定；来源、路线版本和 session 都须属于当前有权访问的 workspace。路径使用现有 managed-path 校验与安全仓库接口，拒绝路径穿越/符号链接，不能直接拼接客户端提供的磁盘路径。公开状态不返回密钥、完整连接凭据或本机路径。

路线设计的目录、理解和路线产物保存在来源目录的新命名空间，不覆盖 `study/result.json`。新完整理解可以通过明确版本转换发布到来源版本列表，旧版本读取仍保持原字节和原 SHA。

新旧来源引用使用区分类型：`legacy_analysis {source_id, analysis_sha256}` 与 `source_understanding {source_id, understanding_sha256}`。新理解可以记录真实存在的 `parent_analysis_sha256`，但全新资料不得伪造旧 analysis SHA。路线集总是绑定已验证的新 understanding；前端版本列表可以并列显示两类，但不混用身份。

拟定存储布局（所有身份由服务端生成；`.json` 仅为说明）：

```text
source/<source_id>/
  study/...                         # 旧分析、检查点和 history 原样保留
  story-design/
    understandings/<sha>/           # 根清单、完整 ledger 分片、覆盖回执
    route-sets/<sha>.json            # 完整不可变路线集
    runs/<run_id>/manifest.json
    runs/<run_id>/requests/<id>/     # prepared、dispatch、raw、parsed、applied
    operations/<operation_id>.json  # 来源设计操作的持久幂等回执
workspace/workshop/source-handoffs/<operation_id>.json
workspace/workshop/sessions/<session_id>/...
```

这些是逻辑目录，实施时沿用现有 workspace 根定位，不改变原数据目录。新的全局默认入口调用 `source-story-design.v1`；dispatch 先读已存在运行的 protocol/capability version，旧 source-study 请求继续走旧处理器，不能直接修改旧 SYSTEM 让恢复缓存失配。能力版本升级只影响新运行或作者明确创建的新设计版本。

交接请求示例（示例 ID/SHA 为占位说明）：

```json
{

  "source_ref": {
    "kind": "source_understanding",
    "source_id": "source-<sha>",
    "understanding_sha256": "<understanding-sha>"
  },
  "route_set_sha256": "<route-set-sha>",
  "route_id": "route_02",
  "mode": "source_development",
  "audience_channel": "female",
  "creative_types": [
    {"id": "genre.romance", "version": 3, "source_sha256": "<saved-type-sha>"},

上例具体标签只有在实际目录存在时才合法。服务端生成选择回执中的 `author_action_ref`、方向选择范围和 session ID，并分别保存 `selected_proposal_ref` 与精确 `author_note`。完整路线不作为请求中的作者 `premise`。

}
```

这只是字段片段，不是完整生产响应。模型使用已有证据/目录 ID；版本 SHA、持久路线 ID、推荐版本和作者选择均由代码绑定，不能由模型补写。

交接是持久状态机：`prepared → selection_saved → session_created → first_turn_queued → first_turn_started/completed`。先落盘确定 session_id，再创建，记录 session 存在后才提交首轮；首轮使用其既有 operation_id 去重。服务在创建后/提交前退出，恢复只补提交；在提交后/本地确认前退出，恢复先查既有首轮回执。不能重复创建讨论、重复发送首轮或把只创建了 session 的状态显示成模型已运行。

旧新建讨论参数的 `source_book` 继续使用原分析绑定和 `_freeze`。新的路线交接使用区分类型的 `source_ref` 与 `source_route_selection`，经新的 `freeze_route_source` 验证 understanding、路线和私有证据包，不调用只能读取旧 Analysis 的 `_freeze`，也不为了通过旧接口捏造分析回执。旧调用无新字段时原行为不变。新来源选择已包含可用路线时默认使用新交接，不再要求用户重新输入同一构想。用户选择“自由讨论”可不选路线，仍有明确的普通入口。

### 7.1 修订请求、并发版本与缓存

持久设计操作还绑定 `source_ref`、基线 understanding/route-set、目标路线的内容版本、反馈记录、有效作者要求版本、类型目录、协议、目标数量和动作计划。先验证权限、版本与目标引用，再提交付费请求；完成后再次核对发布前置条件。来源内容或作者草稿已变化时，已有响应仍保存到它的原基线分支，不悄悄套用到另一版来源。

同一基线的并发反馈使用版本比较提交，禁止最后返回者覆盖先完成者。服务可保留各自不可变分支并显示分歧，或返回 409 要求在更新后重提；无论采用哪种发布策略，已收到结果和未提交意见都不能丢失。查看旧版本只读；作者从旧版本继续时显式指定该基线。选择回执携带路线内容和作者要求版本，过期选择在交接前展示差异，不能自动换成同名新路线。

缓存分层：来源阅读依赖原文/读取协议，设计产物另依赖 exact author request、有效要求、基线路线版本、目标范围、类型快照、模式和输出协议。`entry_origin`（资料库/Workshop 导入）只作 UI 元数据，不进入语义缓存键；两个入口语义相同可复用完整产物。作者明确“再给更多”是一项新操作，绑定当前候选集合和追加目标，不能因为提示文字与上次相同就返回上次两条；网络重试则复用相同 operation_id，不能重复新增。

### 7.2 新建 Workshop 内导入的原位交接

新建表单保存 `draft_id + revision`；导入入口只把资料加入当前草稿并打开共用路线面板，不立即创建第二份讨论。来源上传/解析复用现有资料服务，路线操作读取当前草稿的原样构想与作者有效选择。导入或反馈期间新增的表单编辑保留为新 revision，生成结果显示它依据的版本；模型推荐只提供尚未选择字段的候选默认值，不能覆盖后来编辑的字段。

交接载荷增加 `destination {kind: new_session | workshop_draft | existing_session_revision, id?, expected_revision?}`。有草稿时采用 `workshop_draft`，保存选择后才创建唯一 session；同一草稿已绑定 session 时返回该映射。若产品已预先持久化空 session，则绑定其确切 revision，不能再次创建。草稿映射、选择回执、session 与首轮 operation 必须可恢复核对，崩溃窗口复用已有 ID；路线面板关闭/重开和继续分析都不触发首轮共创。

已有历史讨论不属于“空草稿”：默认导入动作只供查看/提出候选，不改其冻结输入与消息。只有作者明确选择“采用到当前讨论”或“另建讨论”，才分别创建可追溯输入 revision 或独立 session；当前讨论有运行中首轮/交付任务时不修改其已发请求，采纳必须按现有暂停/下一轮修订边界执行。用户已经填写的构想与模型 selected_proposal 分开进入首轮，不能互相覆盖或重复拼接。

## 8. Workshop 共创与完整骨架

首轮上下文必须包含：作者选择事件及原样补充意见、所选路线全文、对应来源理解/原文访问和覆盖身份、作者最终类型知识全文。未选路线可保存在资料库，但不作为本次创作必须满足的事件集合。

### 8.1 原文访问必须由宿主真正执行

当前 `LLMClient.complete(system, user)` 是字符串调用；Workshop 提示也禁止模型执行文件和工具。把文件路径或 SHA 写进上下文，不代表模型能读取。新实现增加服务端共用的 `SourceEvidenceView` 与 `SourceEvidenceCoordinator`，由宿主解析已授权的证据身份、读取原文并实际构造完整请求。

容量足够时直接把必要的完整证据视图、当前完整路线、全部作者原话、最终所选知识全文一起发送，不增加取证调用。分段时采用第 5 节的全量覆盖与回执闭合规则：宿主规划完整来源/台账范围，执行明确的证据整合请求，再产出首轮或交付结果。原文分片可分页，不能把作者要求、当前所选路线或知识全文压缩成近似摘要；若这些必须共同存在的基础内容本身超限，保存进度并报告能力不足。

模型遇到需要补充的依赖时可返回受限结构 `evidence_request {source_span_ids, evidence_ids, reason}`。这是一种响应协议，不是工具执行权。宿主只允许访问本次冻结证据包中已有的代码 ID，拒绝任意路径、URL、SQL 或命令；读取、容量规划、去重和下一次调用由代码负责。此按需请求补充远距离依据，不能替代首次整合的全来源覆盖，未命中的资料不能被当作检查过。

每个证据请求和返回片段实际进入模型的内容都保存请求回执；循环仅在获得新证据或完成新覆盖时推进，同一请求无进展不无限重发。正常首轮“1 次”仅适用于所需完整上下文确实容纳的场景；需要证据遍历时公开记录额外模型调用，不能把它们藏在免费预处理里。

### 8.2 实际接入位置和后续阶段

| 改动位置 | 新合同的接入方式 |
|---|---|
| `api/workshop_delivery.py::author_context` | 新来源上下文通过共用证据视图获取真实内容与权限，返回明确范围；旧 source_context 原投影不改 |
| `api/workshop_request.py::discussion_context/discussion_system` | 新讨论启用受限证据响应类型和已选方向规则；作者原话和当前路线完整保留，不认为文件引用已经被阅读 |
| `api/workshop.py::_complete_impl` | 交给宿主协调器处理证据响应与正式讨论响应；现有取消/超时/费用跟踪覆盖整个实际调用过程 |
| `api/workshop_checkpoints.py` | 指纹加入理解/证据包/选定路线/作者动作/知识快照和实际证据视图版本；已发请求与输出保持冻结 |
| `api/workshop_delivery.py` 及现有骨架分阶段交付 | 全书设计阶段处理全来源影响；章节展开用已完成的全书设计加完整相关原文依赖，记录范围，不能重新丢掉早期未决承诺 |
| `api/workshop_design.py`、`core/creative_execution.py` | 新创作交接版本携带选择出处、证据包身份和访问合同；运行时仍由共用宿主视图发送真实内容，而非仅把本机路径交给模型 |

新增 `creative-handoff.v5`（最终名称随实现固定）只用于已采用新路线证据合同的讨论；v1–v4 的严格字段与冻结行为保持。后续讨论、完整骨架和小说执行均按相同出处/容量规则处理，并沿用作者最新决定。不能只在资料页把内容读全，后面的 Workshop 又退回有损摘要。

### 8.3 可携带的私有证据快照

新交接创建讨论时，服务端生成内容寻址的私有证据包：完整来源文件、索引、台账、理解版本、采用路线及所需引用片段全部包含，逐文件 SHA 可验。使用不可变副本/内容仓库存储，不能依赖会随资料库删除或覆盖而失效的裸路径和可变 hard link。包的完整清单与内容先写完、验证后才发布 session。

从讨论启动作品时，在提交写作任务前把同一包复制/导入项目 `outputs/private/source-evidence/`，并验证清单。私有证据不会进入公开小说导出；正常项目备份/迁移应包含它。这样新讨论和新作品在来源库记录不可用时仍能核对原文。创建过程失败可恢复复制，不重复生成内容；旧讨论/运行中作品不在本次升级中被批量补写证据包。

作者可以明确组合路线，例如“沿用 B 的结局，但采用 A 的身份揭示”。交接保存此原话，并从确切路线版本带入被引用的设计片段与出处，作为需共同协调的提案；不导入其他路线全部内容，也不忽略明确组合要求。无法唯一定位作者所指片段时，只澄清该取舍；不是重新让作者选整套路线。

新选择状态让首轮跳过“开放构想默认三方案”。模型先说明继承了什么、根据作者改动如何调整情绪与看点，再推进一个真正影响故事的未决问题；没有重大分歧时可直接深化，不强制提问轮次。

情绪/看点节点应有稳定 ID，使后续讨论能指向“保留哪份期待、改变哪次回报”，但 ID 只是追踪设计，不成为机械模板。生成完整骨架时传入当前采用路线及变更，而不是重新从最初卡片开始；关键情绪承诺和场面在骨架中有去向，作者明确删改的承诺带变更记录，不复活旧版本。

路线到骨架的落点检查可以在现有交付响应中产生映射并由代码验证引用。不要为每个情绪点新增一轮模型审批，也不要把“计划有对应 ID”表述成正文已经兑现。

旧讨论不自动注入新政策或新路线；作者显式新建讨论时才采用新选择合同。需要在旧讨论重新选路线时使用已有“重新讨论/修改基本设定”语义，先保留旧版本和未发送草稿，不能改写旧用户消息。

## 9. 新旧数据与运行中任务兼容

| 现有对象 | 行为 |
|---|---|
| 无分析的新资料 | 走新整书路线入口；完整理解与路线可同次请求完成 |
| 已完成的旧分析、无路线 | 可直接查看/沿用旧讨论；显式生成路线时按原文/检查点条件补齐理解 |
| 旧单路线 3–6 卡 | 保留为“旧版续写提案”；不能把卡 01/02/03 当作三条整书路线 |
| 正在读取的旧 source-study.v2/v3 | 按旧冻结协议完成/恢复；不在中途切换返回合同 |
| 已有历史讨论 | 保留 source SHA、分析版本、类型版本和全部消息；不批量迁移 |
| 正在写作的小说 | 不读取新路线 latest，不重建细纲、检查点或模型请求 |
| 新路线生成失败 | 已可用旧分析和旧路线继续可读、可选；失败产物与付费回执保留 |
| 原文新增或调整 | 新来源身份/理解版本；旧路线仍绑定旧范围，不能冒充覆盖新章节 |

新请求只与其显式依赖比较：来源变化使相应路线需重新设计，目录变化不使原文阅读失效，模型变化不使已验证来源产物自动失效。部署时不运行写库迁移扫描，不自动购买历史资料升级。

## 10. 回归测试与验收

所有测试先在临时目录、替身模型和独立测试应用中运行。设计 review 阶段不执行真实模型；开发完成后也不自动部署或重启。

### 数据与容量

1. 六章多语种/CRLF/长段落精确重建，Synopsis 与补充预告不挤掉正文，终点正确。
2. 首章伏笔在第六章仍未解决；超过旧 30 项事实时全部保留并参与后续处理。
3. 跨批人物同名、未知身份关系、说谎台词、早期承诺与后期反证不被默认为相同/覆盖。
4. 完整输入用一次请求；分段路径处理全部范围和台账，不能伪造未读范围完成，不能 top-K 漏选；完整请求容量计入系统与目录。
5. 必要证据不可容纳时保留全部输入和已完成步骤；换模型后继续，完成部分不重买。

### 路线内容与类型

6. 每条路线从同一终点到明确高潮/结局；不是为每个原章节各接一段。
7. 来源事实与新秘密分别标注，未读原结局保持未知；重大改写在模式和作者选择范围内。
8. 情绪设计含具体触发、选择、代价和回报；看点与因果相连。替身测试只检验合同，实际创作差异和吸引力另需代表性样本人工 review，不能靠“字段非空”宣称文学通过。
9. 类型来自有效目录，数量/身份/版本正确；改标签保留路线，删除标签只影响选择，不能重新读书。
10. 不接受模型生成的作者批准字段，不把路线预填文本升级为作者事实。

### 幂等与故障

11. 同时双击、两个页面提交、重启后重试都只创建一个设计运行/讨论/首轮。
12. 在每个持久阶段注入崩溃，特别是接收回复未解析、创建 session 未 submit、submit 未落确认；恢复复用结果并保留原响应。
13. 协议纠正只修无效产物；原判断不通过改写 metadata 伪造，连续无进展不无限调用。
14. 暂停 A 不暂停 B；模型参数通过请求注入，不通过全局环境变量串项目；费用按来源/讨论归属隔离。

补充：一条完整已收到的响应恢复不重复发送；对于已发送但未知结果且供应商不支持幂等/查询的场景，测试应断言进入保全状态而不是伪称 exactly-once。候选全局修改后不能沿用旧覆盖回执；输出截断不能通过缩写剧情伪装成完整。

### 兼容与端到端

15. 旧分析、旧讨论、已发请求与运行中小说的受保护文件哈希不变；新功能 GET 没有写操作。
16. 从资料库和 Workshop 内选资料都能“选路线 → 改类型 → 带入 → 深化 → 明确生成骨架”，所选路线及作者改动完整到达首轮与骨架请求。
17. 不重复要求输入构想、不再生成同组初始路线、不把未选路线拼入骨架。
18. 原有全文阅读、资料版本、Workshop 选择/重开、类型冻结、作者权威、骨架交付、运行恢复回归仍通过。

19. 来源阅读已分段完成，但第一次 Workshop 的全来源+完整作者消息+选中路线+完整类型知识不能一次容纳：必须真实执行证据协调、记录完整覆盖与费用，不能只传路径后伪称已读；基础内容本身超限时保全退出。
20. 全新资料无旧 analysis SHA 也能一次理解/路线后创建讨论；旧分析引用仍按原冻结校验；source span 到新证据 ID 的转换不要求模型生成哈希。
21. 创建讨论/启动作品后移除测试资料库副本，私有证据仍可完整核验并进入后续请求；公开导出不含原始资料。对越权证据 ID、任意路径和来自其他 workspace 的引用必须拒绝。

### 新建导入、反馈与路线版本

22. 新建 Workshop 先填写构想/频道/Genre/Tags 后导入六章：所有作者输入完整进入初次路线请求，推荐不覆盖；选择后只产生一份 session/首轮。覆盖无 session 草稿与已有空 session 两种路径，以及关闭面板、刷新、浏览器重试。
23. 资料库与新建 Workshop 导入相同来源/要求得到相同语义合同与缓存复用；仅入口不同不重复购买理解；不同作者要求不能误命中旧设计。
24. “修订 B，同时再给两个方向”形成有序复合动作；只更新授权目标、保留旧版本并追加两条完整路线。重复发送相同 operation_id 不重复追加；作者再次点击“更多”即使原话相同也产生新候选操作。
25. 多次补充要求完整保留：新意见只取代同范围冲突项，兼容旧要求继续传入。原文纠正、作者新增设定和偏好分别标注；不能修改原文件、删除旧命题或伪造作者已批准。
26. 偏好变化不重读无关来源；身份/终点解释变化使实际依赖失效，扩大取证。模型面对原文反证时不能将用户的改编设想标成原文明示。
27. 并发反馈、旧标签页选择和从旧版本继续不会 last-write-wins；原响应各自保存，过期选择得到明确差异；历史路线仍可查看，未选定的新版本不改变已有讨论/运行任务。
28. 很多历史候选与超长反馈下采用完整分页/依赖取回；不得截掉早期约束、来源开放线索或结局。新增路线的实质差异做代表性人工评审，不能以标题不同视作通过。
29. 已有非空讨论导入资料不自动新建或覆盖；明确采纳只产生下一版输入，运行中的冻结请求不变，私有证据包随合法采纳完整保存。
30. 三种 SourceMode 的初次、修订、追加与交接均保持模式：续作从同一已知节点出发，改编遵守作者明确的保留/改写范围，借鉴创作不继承原作人物与伏笔债务；完整来源阅读不因模式而缩水。
31. 开局机制解释有来源依据并标为编辑判断；每条完整路线的第一幕、压力、人物行动与高潮破局方式能从正常输出到 UI、Workshop 及骨架交接完整传递。不同题材的样本不被强制改成生死对抗；分段阅读不因共同提示而越权生成路线，不新增情绪计数/评分门槛。

## 11. 拟实施顺序与 review 后的完成标准

1. 固定领域合同与新旧双读行为；以“共同终点、原文完整、作者选择不升级假设”测试锁定语义。
2. 实现完整证据与容量计划、持久任务/请求恢复；先让全输入路径和分段路径都通过。
3. 实现整书路线与类型推荐；加入内容差异、情绪/看点及原文衔接样本。
4. 实现反馈修订/追加路线、持久选择交接、Workshop 新建草稿内导入、首轮深化和骨架继承；各入口共用。
5. 接入评审通过的前端，完成移动端/刷新恢复/异常状态测试。
6. 完整后端回归、前端测试及生产构建；隔离副本验证所有旧对象不变，提交验收报告。

本轮结束于设计文档和 UI 设计稿 review。后续实现以作者 review 为前提；开发验收结束后仍保持不部署、不重启，等待单独的发布安排。
