# 面向 100 章作品的规划与推演

设计基线为 `dev@a2617c9`，开发分支为 `codex/long-form-planning`。本设计覆盖从立项到可供正文使用的完整大纲。下文的目标架构、发布门槛和阶段二以后的内容属于待实施方案。文末单列已验证的开发进度。

## 问题与判据

在 60 章真实任务上，GPT 的首个全局请求输入为 121,504 字节，两次触发 900 秒超时。第三次返回 60 章路线图。两个缺失的人名引发整份重交，随后第 37 章一个未登记的来源引用使全局设计无法保存。旧 Gemini 任务曾完成 15 批章节设计，初审和修订复核却分别划出 27、29 个窗口。以上是同一本书的两个瓶颈，不能据此推算其他书的完成率。

100 章符合现有章数合同。默认推断可生成五卷，作者明确选择单卷或自定卷界时遵守已确认结果。实际瓶颈贯穿两端，Workshop 要求一次返回全部章卡，staged 运行时又要求一次返回全局设计和全书路线图。若每章路线图大小相近、每批章数固定，把整张路线图发给每一批，单是这项重复传输就随章数近似二次增长。[Workshop 章卡](../../core/story_design.py) · [运行时规划](../../core/outline_planning.py) · [篇幅与卷界](../../core/narrative_format.py)

方案要同时缩短首次可复用成果的等待时间、减少局部修改的重做量、保住全部作者约束，并在正文入口证明这些设计可以使用。工程覆盖率与文学质量分别验收。

## 一份故事设计贯穿所有入口

将作者确认的骨架、后续开发的候选、正式通过的大纲以及正文已发生的事实区分开。文件保存原文与版本，数据库可重建索引。沿用现有 `RunSpec`、`StoryDesign`、`ChapterCard`、`ChapterContract`、原文定位、分卷与结局合同、正文晋级回执。数据转换有显式版本；每个入口走同一个规划接口。

| 入口 | 输入与首次处理 | 对调用方的结果 |
|---|---|---|
| Workshop 新书 | 将已确认的全局设计、章卡、作者最新修订和采用记录一起交接。原文、版本和内容匹配的成果直接导入。将今天的一次全章输出改为按故事段交付 | 作者仍能通读、修改及确认完整骨架，再启动创作 |
| 导入骨架、CLI 全书运行 | 保留原始字节，建立章节、场景和全局段落的来源定位。无法可靠识别的段落进入待归属清单，可扩大阅读范围 | 复用已明确的创作决定，为缺失部分建立工作项 |
| 单独 CLI 大纲、项目大纲操作 | 通过同一接口创建独立规划会话，由现有后台任务机制调度。保留单独生成大纲的返回格式 | 无须启动正文，即可取得相同标准的大纲 |
| 旧任务恢复 | 对旧文件只读导入，在新命名空间建立与旧成果的对应关系，核对模型原始回复、候选、核查回执和来源 | 从第一个缺失的依赖继续，旧任务及其可回滚版本可追溯 |

核心接口只暴露登记或导入作品、推进一个可执行工作项、应用作者修订、发布已通过的大纲。模型、窗口划分、并发数和恢复策略由规划器处理。Workshop 的讨论与确认、正文审批政策以及现有导出合同由各自的原有入口管理。

## 推演顺序与保存单位

1. **登记来源和创作决定。** 为原文片段、采纳决定和结构化字段分配稳定引用，保存原文版本、位置、内容哈希和继承关系。保留原排版、否定词和例外。自由文本中尚无法归属的作者要求要可见，来源变化后重新核对。引用定位成功仅能证明找到了原文。
2. **保存全书骨架。** 全局设计包括故事承诺、主线与结局、人物长期目标、世界规则、重要转折及待兑现的义务。大型人物群和支线可分别形成有引用的成果。各成果有独立校验与检查点，随后做跨成果的矛盾检查。此时不要求模型同时交出 100 张章卡。
3. **规划故事段。** 优先沿用作者的剧情段、卷界与里程碑。缺少分段时，根据不可逆转折和容量提出内部工作划分。内部段可以继续拆小，出版卷界、章号、作者指定事件位置和结局约束单独锁定。段落交接包含进入条件、转折、代价、离开状态与未解问题。
4. **逐步展开章卡。** 每张卡保存人物选择、情绪原因与变化、场景细节、后果、伏笔、回报和需要继承的原文。已确定的场景和好句原样保留，可补充之处明确记录。前后段的衔接依赖满足后才能确认相关章卡。多个独立支线可以在同一已确认版本上并发。涉及同一物件归属、人物知情或关键时间点的工作等待依赖满足。
5. **核查并发布。** 程序检查章节完整性、可解析的引用、明确状态转移、截止章和未覆盖项。模型负责人物动机、因果说服力、情绪和叙事承诺。全书文学审阅以大纲为对象，沿主要故事线串读关键场景，并从结局倒查铺垫。工作分段、后续正文与作者手稿均有独立产物。只有指定版本的必需核查全部完成，才从同一个候选渲染 `foundation.json`、可读大纲和章节执行视图。沿用当前长篇结构校验和正文晋级机制。[可复用的长篇检查](../../core/long_form_quality.py) · [现有发布入口](../../core/orchestrator.py)

## 小上下文连接如何保持完整信息

每次派发先组装实际发送的请求，包括系统提示、方法、作者约束、场景原文、消息封装和工具开销。分别判断传输字节、模型上下文 token 和必要输出空间。有准确分词器或上游计数协议时按对应模型计算。输出须同时满足上下文剩余量与独立输出上限，并考虑后端是否能强制限制输出。不能把网关的字节上限当成模型 token 窗口，也不能把字符估算写成精确计量。来源不明的容量采用已验证的保守档位，记录估算与实际结果；若仍不确定可容纳，先缩小工作项并探测连接能力。

每个工作项声明必须同读的证据、可独立检查的证据及输出内容。构造上下文时，先提供本段原文、当前问题的前置事实、关键变更以及未来承诺。摘要、关键词或检索相似度仅用于找到原件。程序保存随请求实际送出的片段和版本清单。对于所有影响作品的来源，必须有被读取、被继承或经裁定有意舍弃的记录；“有记录”与“语义已核实”是两个状态。

举例，第 8 章甲把钥匙交给乙，第 82 章丙用它开门。工作项同时取第 8、82 章的动作和中间的每次交接，区分真实归属、人物误判和读者所知。若相关来源过多，先按每次交接分别绑定原句和结果，再共同核查有争议的交接两端。若两段不可分割的证据与必要输出仍然放不进当前连接，明确记录哪项判断未完成，其他独立工作继续。允许使用作者已选择或明确允许的兼容连接承接该项，也支持等待容量恢复后续跑。静默截断、模型自动降级、把被省略证据算作已读均不允许。

小模型可接受单章、单场景或单条义务作为工作单位。输出使用稳定 ID 和具体字段；代码负责组装、编号、预算、引用展开及格式。越接近容量上限，预留的回复空间越应由实际任务决定。大型模型可合并独立工作项以减少往返，成果身份和完整性规则相同。分段会增加部分请求数，因此评价端到端耗时、总输入量及可恢复进展，而不能仅看请求数量。

## 一致性检查与修改传播

| 检查范围 | 核查方式 | 何时重新检查 |
|---|---|---|
| 本章与边界 | 核查角色主动选择、承接的具体后果、场景目标与情绪变化，同时读取相邻章的出入状态 | 相关章卡、来源或审阅规则改变 |
| 跨章事实与承诺 | 用人物、物件、知情者、伏笔、义务 ID 连接建立、变化、兑现或刻意悬置的节点，同时保留叙事顺序与故事时间 | 对应节点及依赖其结果的下游变更；有歧义则扩大取证 |
| 整体阅读效果 | 顺读主线与人物弧，检查中段重复、情绪递进、支线交汇以及结局是否挣得；再倒查每项终局义务 | 第一版完成必审。主线、基调、结局或依赖范围未知时扩大复审 |

每条发现记录候选版本、涉及片段、主张、证据、可反驳条件、严重度和影响范围。证据充分的重大矛盾阻断发布；证据不足的重大疑点进入取证；可选编辑意见进入建议。内部元数据语言与正文读者语言按字段用途判断。倒叙、不可靠叙述及作者明确选择的留白应保存解释和适用版本。允许独立问题并行修，但每个候选应用修订前都须核对原值与版本。一次修订后有新发现就创建对应局部工作项，不能据此宣布整书已通过或强迫全书重交。

依赖发现使用原始来源及已确认的局部设计，按“源文建立了什么”正向建索引，再按“后续场景凭什么能够发生”反向查找。初审必须覆盖未匹配的来源、依赖缺口及结局义务。固定相邻窗口会漏远程矛盾；程序推导的依赖也可能漏记。对未能证明修改范围的改动扩大相关故事线审阅，变更作者核心决定可以触发全局复审。

## 调度、恢复与迁移

持久化所需的四种记录如下。实现时优先扩展现有版本化文件和回执读取器。索引允许重建，任何一份已确认的作者输入都能通过原始文件读取。

| 记录 | 必需字段 | 使用规则 |
|---|---|---|
| 来源片段 | 来源版本、原始文档哈希、位置单位与起止位置、逐字内容哈希、归属或未归属原因 | 字符和 UTF-8 字节使用不同单位。读回原件时校验内容；相同文本在多个位置出现时分别定位 |
| 作品成果 | 稳定业务 ID、类型、父版本、来源引用、内容哈希、候选或确认状态 | 例如人物、章卡、剧情段、结局义务。字段修订以原值为条件，写出新版本。作者明确接受的修改优先于较早版本 |
| 故事依赖 | 前置成果及字段、后置成果及字段、关系种类、涉及章节、证据引用、确认状态 | 例如角色甲第 8 章获知事实、第 82 章依据该事实行动。内容修订沿相关字段传播；删改边和未归属的事实也要触发重新发现 |
| 工作与核查回执 | 工作项、实际读取的版本与字段、覆盖范围、核查规则、请求尝试与响应、结果、引用的旧回执 | 只有旧判定通过且所需证据、依赖及规则仍有效才能复用。每个结局义务、故事段和相邻衔接都能反查实际覆盖它的工作 |

规划器先选择依赖已就绪且未被其他执行器持有的工作，再按当前连接的容量和限流合批。阻断问题以涉及的作品事实和引用为身份，同一问题在多个窗口出现可合并证据。新的源文结论可以推翻旧裁定，但重新抽取模型意见本身不足以把同一份被阻断的候选发布为通过。一个没有发生改变的修订应保留初审，转入有新证据的裁决或另一种可验证的修复。

候选产物包含业务身份、内容版本、所用来源、依赖版本、合同和核查规则版本。每次尝试另记实际模型、连接能力、请求摘要、终态与完整响应。工作项身份独立于模型配置；模型切换只影响后续派发，旧成果在来源、规则与依赖仍适用时复用。审查政策若明确要求某种能力，也要作为依赖登记。

程序先持久化派发意图，完整响应先保存，再校验并以版本条件写入候选，最后提交进度。中断后优先读取已存响应补验。用工作项幂等键、执行租约及版本校验防止并发重复提交；迟到结果可以归档，不能覆盖更新后的作者修订。任务取消应传递到模型适配器。一次网络超时只说明客户端停止等待，远端执行状态另行记录。支持上游请求 ID 的连接先查询状态；无法确认时只在安全的系统重试策略下重发，分别记录两次尝试与可能的重复用量，不要求作者填写技术对账。已完成的合格产物不能因本轮连接容量下降而被挡在缓存之外。

对于各版旧检查点，先验证原任务身份、原文和产物哈希，原文件保持只读。在独立命名空间导入能验证的全局设计、章卡、原始回复与核查回执。裸回复可以作为待校验候选；旧协议缺少覆盖证明时补验缺口。关闭并重启后重复导入的结果必须一致。正在运行的旧任务由当前执行器完成或安全暂停后交接。新发布指针只在所有产物齐备时一次切换；回滚指回原版本。未确认的修改和已发布正文都不得被迁移覆盖。

## 角色与系统分工

详见[按调用路径核对的角色对照](2026-11-09-runtime-agent-roles.md)。沿用 Architect 对创作计划、Scribe 对正文、Editor 对修订、Guardian 对连续性、Curator 对声音的职责。跨章规划采用持久化工作项驱动，角色按工作项读取有来源的材料。可计算的约束由代码处理。角色可以共用一个模型连接，也可按配置选择不同连接。创作判断与复核使用独立的输入视图、结果和权限，同一角色的名字并不构成独立验证。正文采用现有通过即晋级、出现必要问题再修订的机制，不增加五轮逐章规划投票。

## 交付顺序与验收

| 阶段 | 交付物 | 通过条件 |
|---|---|---|
| 一：现有流水线中的有效改进 | 复用上下文和规则完全相同的通过回执；降低窗口准备开销；验证字段级纠错 | 合成 100 章从正常入口走完大纲，修改边界章时两边重验；覆盖、修复结果及恢复语义可查。以保存的 60 章回复回放，分别记录可自动处理与仍需取证的问题 |
| 二：统一规划成果与小上下文调度 | Workshop、导入、全书任务和独立大纲入口共用产物；按段生成、实测容量、两种旧格式迁移 | 8k、16k、32k 为测试配置，另测 UTF-8 传输上限及未知容量。任何派发均符合测试连接的实际约束；最小必要材料无法合看时不产生通过记录 |
| 三：跨章因果与增量审阅 | 正反向义务追踪、字段变更传播、全书文学审阅、故障注入与灰度 | 测改措辞、改道具持有者、改凶手三种影响范围；验证迟到结果、重复恢复、规则变化和切换连接。对照单书记录改动后重做范围与硬矛盾漏报 |
| 四：真实长篇对照 | 用授权测试书、冻结的输入及模型配置，比较基线和候选，从两种新书入口运行到大纲发布并读取正文计划 | 至少覆盖 3 种结构的 100 章作品，包含单卷、多卷和多视角或倒叙，分别记录 GPT、Gemini 及一种真实小窗口配置。逐项公布完成数与分母、失败归因、全程耗时、首次检查点时间、输入输出用量和重复调用 |

工程用例要求预设的关键矛盾全部命中、故意误导及知情差测试不误阻断、源文及已有产物可逐字追溯、有效结果在无修改恢复时零次重新生成。文学对照由不知版本的编辑阅读原始大纲、首中尾正文样章和有关联的跨段场景，记录人物动机、情绪递进、揭密、伏笔与结局的具体得失。任何可复现的重大故事退化都会阻止切换默认。提速以相同输入、同模型同档、同一质量标准下的配对耗时和用量为准，小样本逐书列值。扩大灰度前再评估分位数、完成率及成本，合成测试无法给出商业完成率。

上线先在项目副本运行，按创建版本固定旧任务的读取器。通过上述对照再逐入口切换默认。面向作者只展示已确认的成果、当前剧情范围、剩余影响及可执行的创作决定，模型计数与传输诊断保留在技术日志。
