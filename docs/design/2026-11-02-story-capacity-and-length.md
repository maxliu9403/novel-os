## 1. 问题与目标

当前创建表单收集章节数和平均章长；全局设计、完整章表和交付随后锁定章数。缺少在故事成形后重新核对“关键时刻能否展开”的环节。章数一致是结构正确，不等于容量适合；现有长篇适配分数也不能证明具体场景有足够篇幅。

目标是先确定有价值的故事，再为它安排篇幅。不可通过暗删作者选择、压缩成剧情摘要或增加重复段落来满足数字。也不可把“更长”等同于精彩，或允许模型无限扩展。代码负责完整性、版本、算术与确认；文学效果由实际正文和读者反馈判断。

区分三个对象：

| 对象 | 含义 | 谁决定 |
| --- | --- | --- |
| 用户篇幅偏好 | 想读短篇、倾向短章、预计阅读规模；可有真正固定的交付限制 | 用户，可修改 |
| 故事容量建议 | 为已选故事保留关键场面所需的场景组合、总量区间和章节方案 | 模型提出，附具体理由 |
| 已确认执行篇幅 | 本次采用的章表、各章目标、全书目标、计数语言与版本 | 用户确认后代码冻结 |

章数是初始偏好，每章设置是未确认方案的逐章目标规划上限。需要更多空间时，保留故事并增加章数。用户同时明确固定章数和章长时，须先协商约束或故事取舍，不得后台加长章节或悄悄删戏；实际正文不在数字边界截断。

## 2. 在现有共创中推导，不再加一轮独立评分

### 第一步：先把故事走向想完整

沿用当前故事地图，确定开篇关切、人物欲望和阻力、重要转折、高潮选择及结局回报。创作初期只显示初步范围；不因信息还少就要求用户逐项批准场景。作者仍只选择宏观走向，细节由模型处理。

### 第二步：把重要节点转换为场景需求

每个场景或连续场景组记录：

- 来源：采用的故事节点、角色关系或回报ID。
- 读者价值：为什么值得在场经历，删掉会失去什么。
- 起始处境、人物要什么、阻力、回应与结果；静场可记录理解、关系或情绪如何变化，不强制每场都有反转。
- 表现方式：完整现场、短场面、过渡概述；重要离别、承认、拒绝、发现、高潮和余波不能全部降为概述。
- 需要的铺垫及后续影响；可合并场景与不可合并的理由。
- 以正文语言计的篇幅区间及理由，列明不确定性。

记录/条款/世界规则要在人物使用它们做选择时产生压力。不要把规则介绍数量当成故事复杂度，也不要为了“戏剧性”给静场添袭击、给配角添恶意。

篇幅估计没有“一个事件等于多少词”的固定算法。对话分量、视角距离、行动清晰度、心理阻力、气氛与余波共同影响估计；中文按字、英文按词分别建口径，不做固定倍数换算。模型估计是待验证的编辑判断。

### 第三步：先分配总量，再组织章节

按场景依赖和阅读节奏编排；章末落在有意义的完成、变化或期待处，不为满足平均数硬切。允许关键章较长，过渡章较短，高潮后的余波获得独立空间。

代码核算场景组区间与章目标，识别分配遗漏、重复、跨章分摊重复计算、总量不一致。它能检查“承诺的安排是否自洽”，不能认定1200词必然够写某场戏。

通常只给2–3个方案：

1. 保持章数，在每章规划上限内调整分配：保留全部已选场面；无法容纳时不提供可直接采用的超限方案。
2. 保持故事与总量，增加或减少章数：改变阅读节奏，不自动改变故事规模。
3. 若有严格总量上限，提供明确的改写方案：列出合并/取消的具体支线和影响；涉及已选事实必须重新采用，不能默认执行。

若现有设计本来能适配，不为凑方案制造多余选择。故事确定、容量没有新问题时主动推荐生成骨架，不反复微调几十词。

## 3. 用户交互

新建小说保留当前统一面板。篇幅默认选“根据故事推荐”，提供短篇/中篇/长篇的偏好说明；章数和章长移入“我有明确交付要求”。不凭某个题材默认锁死固定章数。

故事地图附近显示一张“篇幅建议”卡：

> 已确定主要故事与结局。原期望12章、约7,200词；建议12章、约13,200词。
> 原因：母女离别、两次信任变化、危险交班和恢复余波需要现场展开。
> 保留全部已选剧情；不新增支线。估算调用成本另列，未知费用明确为未知。
> [采用12章方案] [查看另一种章长安排] [补充限制]

主按钮“采用并生成骨架”可以把确认与已有交付请求原子提交，不强迫用户多点一轮；只有用户点击才调用模型。单纯查看、切换方案、刷新不增加调用。确认前能展开每章承担的场景和分配理由，不向普通用户展示JSON。

重大故事修改使建议过期。旧选择保留，但必须看到本次改变了哪些场景、预计增加多少，而不是无提示覆盖。当前骨架已存在时，显示“修订后重新确认”，保留上一版和原准备命令的失效记录。

## 4. 私有数据合同与代码职责

建议由一个 `StoryCapacityPlan` 模块拥有解析、校验、确认和冻结接口，Workshop/API/执行引擎只消费同一份结果。不建立相互竞争的题材容量表、UI章表和执行章表。

早期设计示意字段（不是H5字段；实际首版接口以 `core/story_capacity.py`、`api/workshop_capacity.py` 为准）：

```json
{
  "schema": "story-capacity.v1",
  "source_sha256": "hash-of-author-approved-design",
  "language": "en-US",
  "count_unit": "words",
  "preference": {"chapter_count": 12, "strict_count": false},
  "scene_groups": [{
    "id": "scene_01", "source_refs": ["beat_01"],
    "presentation": "on_page", "reader_value": "本书具体阅读价值",
    "estimated_range": [900, 1300], "estimate_reason": "本书具体场景理由"
  }],
  "options": [{
    "id": "option_A", "chapter_count": 12, "target_words": 13200,
    "chapters": [{"number": 1, "scene_group_ids": ["scene_01"], "target_words": 1200}],
    "story_changes": [], "tradeoff": "保留章数，单章更充分展开"
  }],
  "selected_option_id": null,
  "confirmation": null
}
```

示意仅写一章，不可直接作为完整12章合同。正式结果要求1..N完整连续章表，全部必须保留的节点有映射，分配总和等于采用目标；区间有序、数值为有限正整数、单位明确。跨章场景须拆成子段并记录父ID，防止重复计数。无依据的“已核实”或“质量通过”不在合同内。

确认接口绑定会话revision、故事源hash、候选hash、option_id和幂等request_id；重复点击返回原结果，不二次推理。基础设定的平均章长是派生展示，不能反过来抹掉各章差异。`prepared`及运行交接绑定完整合同hash；重新分配后失效旧启动命令。

自动规则可以阻止错版本、漏章、漏映射、未确认变更、目标总量不一致及超平台上限。对于“这场戏可能写得太略”的文学意见，展示来源和建议，不升级成无限重试的机械门禁。

## 5. 骨架修订与正文执行

骨架生成前在原有全局设计回复内输出容量建议；确认后才锁定完整章表。不要生成全书后又从零重新推导一次。保存所有完整阶段，恢复只补缺失部分。

交付复核发现明确问题时，应关联到具体章节/规则/原文位置与修正结果。下一阶段新增结构化修订记录：`finding → proposed_change → applied_revision → recheck`。局部措辞和重复可直接在授权范围内修正；改变人物选择、结局或总量仍需确认。最多使用既有有界修订预算，失败保留结果，不额外增加自动文学审查循环。当前行政导入工具已能安全保存人工完成的修订，但尚不等于自动关闭模型发现项。

M2接收完整已采用合同和各章场景目标。章长是写作目标，不是到字数就截断的阈值；重要变化必须通过实际段落兑现。达到字数也可能只有摘要，偏离目标也不必然质量差。

已写章节不因为后续容量变化自动重写或重编号。若发现剩余篇幅确实不足，在章节保存后的检查点说明：新增了什么必要空间、哪些既定承诺尚未兑现、对剩余章节/总量/成本的影响。用户选择调整剩余计划后再继续；不得静默扩书、反复中断每章或把超时当作创作不够好。新增场景若没有独立价值，先删重复，不能自动索要更多章节。

M3继续显式阅读真实正文，重点观察开篇投入、中段是否重复谈条件、高潮行动是否可辨认、余波是否真正兑现。与计划对照用于找漏项，阅读评议本身不因大纲写了情绪就判读者已被打动。

## 6. H5、旧任务与失败恢复

- 私有容量/文学评议不进入H5清单。正式产物仍由代码构建Manifest V4、`novel-h5-import.v1`、`ready`，正文来自EPUB；发布分类沿用固定字典。
- 章数或分卷改变后，从新确认的同一源重建章映射、EPUB spine、publication package及相关SHA；不能仅修改Manifest数字。
- 保持ZIP≤64MiB、内部EPUB≤16MiB、spine≤512；有一篇开头Introduction时最多511篇正文。封面PNG/JPEG；这些上限由验证器检查，不是提示模型“尽量遵守”。
- 源、配置和已确认合同变化后，旧候选/准备命令不可被恢复为新结果；旧文件与已消耗费用保留。停止/失败不自动购买新调用。
- 旧会话、已写正文、旧导出包不自动迁移。先验证新协议在新讨论有效，再提供显式升级；没有容量合同的旧任务保持旧行为，不能凭当前新默认回填。
- 模型辅助容量字段坏了，保留有效讨论正文，清楚提示建议未就绪；不要把无效建议当成用户同意或额外自动调用。

## 8. 实施顺序和验收

1. 先完成本次明确骨架修订、安全版本化导入、组装去重及通用场景指导（本轮范围）。
2. 在现有讨论返回中接入可选容量计划，增加确认卡/服务端原子采用，替换新建时过早冻结数字；不增加独立模型请求。优先实现单部作品，再覆盖多卷/系列当前册，未覆盖模式保持旧流程且明确提示。
3. 将已确认计划贯通章表、执行交接、规划/恢复与导出；补齐已写作品剩余容量变更的显式流程。之后才开放旧会话升级。

工程测试：不同语言、不同模式、混合题材/无资料；范围合法、总量一致、场景不遗漏；冲突方案不能绕过确认；刷新/重复提交/并发旧版本/暂停恢复不重复调用；全量旧合同回归；H5真实验证器检查重建包。

创作验收：用不同题材的冻结输入及相同模型预算做可比较样本，读前三章和高潮余波，再读完整书；报告具体正文证据与负面样本。分别评价因果、人物、类型体验、场景表现、情绪变化及回报。不以字数增长、单本自评分提高或输出无报错宣称所有小说质量已保证。
