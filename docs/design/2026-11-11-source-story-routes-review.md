## 2. 用户真正要作出的决定

资料分析的交付目标是帮助作者判断：**基于全部已提供的资料，哪一种完整故事值得继续开发，它会给读者什么体验？**

流程为：

```mermaid
flowchart LR
    A[全部已提供资料] --> B[共同的故事理解与已知终点]
    B --> C[2–3 条完整故事路线]
    C --> D[比较情绪、看点、因果与结局]
    D --> E[选择路线并调整 Genre / Tags]
    E --> F[头脑风暴深化已选方向]
    F --> G[作者请求并确认完整骨架]
```

原故事推演的每条路线从同一个有效正文终点出发，覆盖主线推进、重要转折、高潮与收尾。改编重写按作者明确的保留与改写范围设计；借鉴创作独立构建人物、因果和结局。一个来源中的多个独立故事保留各自终点，不能混成一部续作。Synopsis 的宣传承诺和补充预告不被当作已经发生的正文。

本次 review 补充两项正式设计范围：**新建头脑风暴时直接导入作品，也在当前草稿内选路线**；**作者可以反复补充提示词，继续修订或追加选项**。资料库与该入口共用后端和路线组件，保留已填构想与明确的题材选择。上述交互已进入业务实现；独立原型仅保留早期样例。

提示词核心已按作者提供的**商业主编版**采用：增加开局代入机制、人物欲望与权力变化、具体第一幕、抉择代价和高潮破局。补充三项执行边界：张力服从题材而不固定成生死/暗黑；开局吸引力不变成逐章钩子表；文学要求不新增机械评分和固定审稿门槛。后端输出与 UI 展示同步实现，提示词尚未进行真实模型文学评测。

## 3. 情绪与看点是一等设计内容

路线卡的第一层展示“读者为什么在意、会期待什么、最终得到什么”，不让作者先阅读协议、长篇摘要或章节清单。

| 内容 | 必须具体到什么程度 | 不接受的替代物 |
|---|---|---|
| 读者情绪承诺 | 在意哪个人的哪种处境，期待什么改变 | 只写“爽、虐、甜、燃” |
| 主要看点 | 谁在什么局面下作出什么选择，谁付出代价，关系或局势怎样改变 | 抽象“增加反转”“增强张力” |
| 情绪推进 | 触发场面 → 人物选择 → 代价 → 读者期待变化 → 回报 | 给各阶段机械打情绪分 |
| 长线悬念 | 读者持续想知道什么，如何逐步改变理解，最终怎样回应 | 每段结尾都强行留下悬念 |
| 高潮与结局 | 事件结果和关系/情绪承诺同时得到交代，留有必要余波 | 只解决外部事件，人物体验悬空 |
| 路线差异 | 核心选择、对抗方法、关系走向或最终回报具有实质差别 | 相同故事换名称和标签 |

情绪可以通过安静的理解、关系修复、失去后的接受等方式兑现，不要求所有路线都有同一套反转、惩罚或团圆。精彩场面要嵌入完整因果；不能堆一组互不相干的“名场面”。

不展示未经真实读者测试的留存率、吸引力百分比、商业成功分数。情绪设计属于创作意图，不能宣称已经证明阅读效果。

## 4. 已确认的五项产品决定

作者已批准以下默认设计，实际实现与验收状态见报告。

| 决定 | 建议方案 | 用户可以怎样改 |
|---|---|---|
| 路线数量 | 默认三条，允许两条具有实质差异的完整路线；追加默认两条，数量是单次目标而非历史总上限 | 保留旧方案后继续新增，或只完善指定路线；不为了凑数复制故事 |
| 路线展开程度 | 卡片先展示情绪承诺、核心看点和走向；展开后可看完整因果、高潮、结局 | 在头脑风暴中修改关系、冲突、结局等重大选择 |
| Genre / Tags | 按每条路线的实际故事机制推荐一个 Genre、1–2 个 Tags，并给理由；读者方向可编辑 | 作者修改覆盖推荐，完整记录最终选择 |
| 选择的含义 | 选择“讨论方向”，模型提出的具体事件继续是可修改设计 | 补充明确的保留项、修改项，或后续重新讨论方向 |
| 进入讨论 | 一次提交保存路线选择、题材和作者补充，进入已有 Workshop；首轮直接深化该路线 | 可以先只看路线，也可在未定方向时进入开放讨论 |

不要把“推荐”做成作者已经点击的选择。若作者尚未选择任何路线，卡片的主按钮应明确指向具体路线，不能暗中采用默认推荐。

路线区常驻“我想调整 / 补充的方向”输入，提供“按补充完善方案”和“保留已有，再给新方案”。一次意见可以同时指定保留项、修订目标和新增方向，不能被按钮模式截断。意见原话与各版本都保存；作者可以比较变更，也能选择旧方向携带最新要求进入讨论，不必先反复重跑分析。原文理解被纠正时回查实际证据，偏好调整复用未受影响的阅读结果。

## 5. 后端方案的关键约束

### 5.1 四种内容分别保存

1. 原文资料及其证据定位。
2. 从资料中提取的事实、歧义、知情范围和未决线索。
3. 模型生成的整书路线及其新增假设。
4. 作者选择方向的行为，以及作者亲自填写的补充文字。

路线不会整段伪装成作者的 `premise` 或用户消息。现有 Workshop 会将这些字段作为作者依据，因此新入口必须保留内容来源，不能靠自动填一个大文本框完成交接。

原文证据 ID、版本和校验值由程序管理；模型负责判断和创作，使用给定的证据 ID，不承担重抄引文、计算 SHA 或生成文件位置的工作。

### 5.2 小上下文下的完整性

容量允许时，共同读取完整原文并生成路线，避免无意义分段。需要分段时，原文、已抽取记录和未决事项全部保留，按来源建立覆盖与引用记录；合并不能减少既有记录或只留下再次概括后的摘要。

跨段因果、人物知情范围和重大反转依据必须能够回查原文。仅按相似度取少数片段，不足以代表整份来源。必要依据不能容纳时，增加有记录的阅读/整合步骤；仍不能满足时保留进度并明确说明范围，不以删资料换取“完成”。

覆盖回执同时绑定路线版本。后续批次修改路线后，必须复核修改影响到的早期依据；不能让旧候选的“已处理”标记为新候选背书。原文的重要开放线索不能由模型随意标为“范围外”而跳过；范围外只用于明确独立的其他故事/非叙事材料，或作者明确调整的范围。

必须分别报告三件事：

- 全部原文是否完整发送过；
- 所有已记录事实、未决线索和依赖是否得到处理；
- 文学理解与路线质量的评阅结论。

前两项有工程可验证证据，不能冒充第三项的保证。模型没有抽取出来的重要线索需要通过原文覆盖检查和针对性反例评阅发现。

### 5.3 避免重新变成重型核查流水线

- 所有路线共享同一份来源理解，不为每条路线重复读取原书。
- 分类推荐和路线设计尽量在同一正常输出中完成；选择后的完整题材知识通过现有 Workshop 注入。
- 正常读写路径不新增多角色全书终审、情绪评分器或逐章钩子校验器。
- 结构错误、缺失证据和真正的原文冲突分别处理；没有问题的部分保留，修订围绕已定位的问题进行。
- 完成的原文阅读、路线版本和模型回复可以恢复复用，费用调用与状态记录可追溯。

### 5.4 新旧数据独立演进

新路线集是单独的追加版本，绑定所依据的来源和分析。旧 `continuation_plan.cards` 继续显示为历史单路线提案；不能直接当成多条整书路线。

新功能不改写旧分析、旧请求提示或检查点哈希。正在分析的任务继续其原协议；历史讨论和正在写作的作品继续其冻结版本。作者主动为旧资料生成新路线时，新结果另存，缺少完整证据记录的旧摘要不能被包装成已完成全量理解。

### 5.5 交接是一项可恢复操作

创建讨论、保存选择与启动首轮讨论要有持久的操作记录。同一次点击重试、双击、断网及进程崩溃只能恢复到同一份讨论和同一轮请求；不能依赖前端连续发两个请求碰运气。收到的原始回复在解析前保存；未知的远端结果不得擅自当成失败重复付费。

本地可以保证唯一创建和唯一采用。对于没有请求查询或幂等能力的模型服务，不能承诺网络中断后的远端扣费恰好一次；方案必须保留未知状态，优先自动核查，不让用户填写技术对账，也不靠盲目重发假装恢复成功。

未采用路线保留在来源版本中供以后比较，不进入当前作者要求。用户改 Genre/Tags 不触发重新分析原书，也不静默替换选中路线；在讨论中说明所需的创作调整。

## 6. UI 信息顺序

1. 页面上方：资料范围、已知续写起点、当前版本，历史版本可查看。
2. 路线比较：情绪承诺、核心看点、路线差异、推荐理由；主按钮清楚指向所选路线。
3. 路线详情：完整主线、人物/关系弧、主要场面、情绪变化、悬念与兑现、高潮结局；原文依据折叠显示。
4. 补充分析区：可指定路线，输入意见后完善方案或追加新选项；保留版本并展示具体变化。
5. 选择栏：推荐题材、用户最终选择、可选作者补充；不用重复填写构想。
6. Workshop：显示已选方向及作者意见，第一轮给出深化方案；后续明确请求才交付完整骨架。

“章末钩子”在路线层改为“全书悬念与兑现”。这涉及提案协议和设计尺度的变化，不只是文案替换。章节级钩子留在后续骨架设计中。

## 7. 实现顺序与验收门槛

| 阶段 | 交付 | 进入下一阶段的证据 |
|---|---|---|
| 设计评审 | 本稿、后端方案、UI 方案、独立原型 | 作者确认或提出修改；目前停在这里 |
| 资料与路线核心 | 来源索引、完整证据记录、路线版本、生成与恢复 | 小容量/长章节/错序/跨段线索/协议错误等离线回归 |
| Workshop 交接 | 幂等采用方向、分类版本、作者意见、首轮深化 | 不重复创建/调用，不升级模型假设的权限 |
| 前端全入口接入 | 资料库、创作资料选择器、历史版本、讨论入口 | 可访问性、响应式、刷新恢复、选择及字段一致性 |
| 综合验收 | 后端/前端完整回归、历史数据隔离回放、设计样例评阅 | 结果和局限明确；不把替身测试称为文学成功 |
| 部署 | 本次不执行 | 需要后续明确的部署指令 |

必须包含的回归场景：六章共享唯一终点，早期未决线索跨段保留；补充预告不推进时间；不同路线不串设定；只返回空泛情绪标签的候选不能算完成设计；一次选定后不会重置三条方案；编辑题材后刷新不丢；交接崩溃后复用已保存回复，未知请求不盲目重发；原历史文件哈希不变。

设计原型的点击检查只能证明交互可评审，不能替代上述业务实现回归。本轮不使用正在创作的小说作为开发测试数据。
