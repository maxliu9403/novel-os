# 头脑风暴：选项式共创与主动收束

状态：2026-11-01 已按用户批准方案实现并部署 localhost:5174，工程验收完成。真实模型的选项质量、主动收束效果和耗时变化待作者继续样本验证。实现、验收和回退见[交付记录](../reports/2026-11-01-workshop-guided-convergence.md)。

用户明确的新要求：模型承担提出故事方案的主要工作，作者通过选择并补充开放式想法参与；模型适时提示可以生成骨架，避免讨论一直扩展。保留作者继续打磨和修改决定的自由。

提案检查时修订 9 正在处理用户定向修改。实施期间作者继续讨论，部署前已到修订 12、draft、无错误；本轮未改其输入、策略或任务。以下是提案时的设计依据。

提案时的源码状况：

- `api/workshop_design.py` 保存方案、采用记录及必填 `next_focus`，没有独立的全书设计覆盖和生成建议状态。
- `web/src/components/WorkshopDesign.tsx` 的方案选择默认折叠；采用仅保存，不调用模型，随后需要再发送继续推导。

## 2. 作者看到的每一轮

主区域按以下顺序展示，沿用当前浅蓝紫、白色面板与深色主按钮：

1. **本轮决定什么**：一句话说明当前关键分岔；简短说明继承了哪些已定选择。
2. **可选择方案**：关键分岔默认给 2–3 个具体选项，标注一条推荐及原因。
3. **补充想法**：始终可见、可留空的自由输入；作者也可完全不用选项，直接提出另一条路线。
4. **本书进展与下一步**：已形成什么、仍缺哪项核心决定、是否推荐生成骨架。
5. 完整剧情推演、题材机制与历史记录折叠查看；所有原始内容完整保存。

每个选项回答「发生什么 → 人物如何选择 → 失去与得到什么 → 后续关系或结局怎样变化」。不能只写“更爽、更虐、更悬疑”。选择负担控制在一轮一个主要决策组；紧密相关时可以有第二组，不为细节连续列问卷。

局部改名、明确修订、解释性提问及已经收束的轮次直接处理，不强行凑出三条选项。作者已固定的主线不在每轮重新开局。没有推荐理由时不得为了界面默认勾选。

## 3. 选择、补充和模型调用

- 点击卡片只是选中，可切换；不立即调用模型。
- 「按所选继续」一次提交所选方案与补充意见，并明确启动一轮讨论。留空补充也能继续，作者无需重复输入“同意”。
- 只有自由文本时显示「发送想法」；作者说“按推荐推进”在本轮明确范围内有效，不视为授权无限自动讨论或生成正文。
- 保留「仅保存选择」次级操作，兼容现有采用行为，作者可以稍后继续。
- 「都不合适，换一组」是明确的新一轮请求；可以附原因，不静默产生额外备选调用。
- 相互替代的路线默认单选。若作者想把 A 的人物关系和 B 的结局组合，保存原话并由下一轮解释能否兼容、调整后的因果及取舍，不把两套互斥事实直接合并。
- 所选方案与开放意见有冲突时，以作者的新明确要求为准；若含义不明，只询问影响走线的那一处分歧，并给可选解法。

选项、自由文本、决定来源与本轮启动应作为同一修订检查下的操作保存，带幂等请求 ID。双击、刷新或网络重试不得启动两次调用；失败仍保留本轮完整输入。已采用的历史方案不能因卡片样式变化而丢失。

## 4. 有目标地推进到全书走线

使用可折叠的四项设计概览，状态展示「待设计／已有提案／已有作者依据／需协调」，不显示虚假的文学完成百分比。“已有作者依据”包含明确采用或委托，是模型对原话的解释，精确引文检查不代表代码验证了语义或文学质量：

| 设计范围 | 需要形成的实质内容 |
| --- | --- |
| 核心故事与题材 | 主角追求、主要阻力、失败代价；题材机制怎样改变主要选择 |
| 人物与关键关系 | 欲望和冲突、对抗者的应对、重要关系的变化 |
| 转折与高潮 | 起因到重大转折、高潮之间的因果；伏笔和回报的初步安排 |
| 结局与阅读体验 | 最终选择、代价与结果、主要承诺的兑现；篇幅能承载这些内容 |

这是覆盖视图，不是四个必须分别确认的页面，也不要求每格新增模型调用。已有完整构想可以一次覆盖；作者重大修改只重新评估相关部分。

下一轮优先处理影响全书的空缺。在结局和高潮仍未形成时，避免持续扩写规章、职业细节和支线。连续几轮只润饰同一节点却未推进主线时，下一轮明确转向全书走线或指出真正阻碍收束的决定；不后台自动发起一轮。

## 5. 主动提示可以生成骨架

独立增加「建议生成骨架」状态，与现有“完整骨架已生成、可确认”的 `ready_for_confirmation` 分开。

建议生成的依据：

- 有清晰的主线目标、主要冲突和题材作用。
- 主要转折能够通向一个已有依据的高潮与结局。
- 关键人物选择、持续代价和主要回报已经形成。
- 没有尚待作者解决、会改变故事方向的冲突；核心方案已有采用依据，或作者明确委托模型决定。
- 组织形式、语言、篇幅和受众足以支持后续章表设计。

具体姓名、场景对白、道具、完整逐章细纲和导出 JSON 不必在头脑风暴期逐项讨论。模型可在作者已选择的走线内，生成骨架时补全实现细节；不得借补全改变已确认的核心关系或结局。

推荐卡示例：

> 故事已具备生成完整骨架的条件。主线、关键转折和结局已确定；接下来会展开章节、伏笔回收和人物资料。
>
> **生成完整骨架（推荐）**　继续打磨

尚有核心选择时，给出「还需要确定结局的代价」及对应 2–3 个选项，不笼统地反复“继续完善”。

达到建议条件后，默认推荐生成，不继续制造新的分支；作者选择继续打磨时继续服务，没有固定强制轮数。进度卡不是新文学评分门，作者仍可主动要求生成；如果存在关键未决，说明内容并支持明确委托推荐，不要求为了凑轮次再次讨论。

「建议生成」只是设计建议；真正执行必须由作者点击生成或通过既有明确交付操作触发。生成成功后显示「下载骨架 MD」；下载不调用模型。启动正文继续是另一个明确操作。不得把“可以生成”写成“已通过正文质量验证”。

## 6. 模型与代码各自的责任

模型负责有差异的选项、故事判断、推荐理由和设计覆盖建议；代码负责身份、来源、状态、作者选择和执行边界。代码不能仅凭 JSON 字段齐全证明故事好看。

复用现有方案和决定记录，增量补充：

- 决策组及范围、选项关系、推荐理由，选项 ID 由服务端分配。
- 全书设计概览：覆盖项、简短内容、依据的消息/方案引用、仍缺的关键决定。
- 下一步建议：继续选择、局部调整或生成骨架，附理由。
- 源讨论修订及策略版本。作者新意见使关联建议待复核，旧“可以生成”不能套到已改变的故事上。

模型的“已确定”描述必须有作者决定或委托依据，模型无权写作者采用记录。自然语言选择仍有效，不能为了结构化强迫重按按钮。匹配不明确时保留原话并展示待确认，不能把所有待定提案当作已采纳。

补充字段缺失或格式异常：保留有效回复，提示本轮进展未评估；不丢弃故事内容、不自动重试、不阻断既有显式骨架交付。讨论记录与新版状态不进入 H5 发布元数据。

## 7. 控制等待与兼容边界

- 选项、推进状态和收束建议在原讨论请求中同时返回，不增加专门的“是否成熟”模型调用。
- 一轮只解决最关键的 1–2 项设计问题；简短选项优先，详细论证折叠，避免反复展开整本设计。
- 先排查并删除同一请求中的重复资料；不默认截断作者原文、已确认决定和题材限制。历史压缩若需要，另设来源保留和回归验收，不用未经验证的摘要替代事实。
- 时间、Token 和可用建议数量共同记录；模型配置的调整需要真实对照，不能以更短回复声称已经提速或质量不变。
- 新讨论采用新版策略。旧讨论保持版本和历史；启用增强需要在空闲状态明确采用并记录升级，不重建已有故事或覆盖正在运行的请求。读取旧会话零写入、零调用。

## 8. 分步实现与验收

1. 先做后端协议与记录：决策组、覆盖建议、来源修订和推荐生成状态，保持讨论/交付分离。
2. 再改前端：展开关键选项、选项＋补充一次提交、可折叠设计进度、生成推荐卡。保留现有视觉与刷新恢复能力。
3. 同步应用提示和仓库 Skill；本机安装副本单独核对，不能假定自动同步。
4. 工程验收后再约定真实样本继续验证，运行中的用户样本不自动升级或追加调用。

工程验收包括：仅点卡片无调用；提交选项＋补充一次调用；双击/刷新幂等；互斥项不双采用；自然语言与后续修改保留；缺可选字段不丢回复；建议状态无法自行生成骨架；生成带入未发送补充；重大修改后旧建议失效；旧讨论和 H5 协议不变。

真实质量验收观察：作者只选择也能把故事推进到结局；补充想法能改变后续；关键选项的选择与代价确有差别；题材进入关键场面；有依据时主动推荐生成，尚有核心矛盾时说明具体缺口；局部修改不会反复重选全书。以真实产物和阅读评议判断效果，不把卡片数量或轮数当作质量。
