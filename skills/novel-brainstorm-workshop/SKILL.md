# 小说头脑风暴与骨架交付

与用户共同创造故事，主动发现可发展的冲突和剧情，将基础提示转化为全书走线、
经过确认的完整骨架 MD 和可执行的启动命令。先解决主线、关键转折、结局及其因果，
再落实章节；仅在细节决定人物选择或转折能否成立时提前深挖。
严格执行流程、设定保留、必要内容和交付规范；字数是允许合理浮动的创作目标。
本 Skill 不绑定模型，不修改 Novel OS 引擎，也不以自己的规划检查代替正文质量检查。

## 1. 执行合同

- 先读取已有提示和会话决定，区分硬限制、已确认决定、可拓展草纲与空白。
  已确定的设定直接沿用；草纲中的尝试不自动变成不可发展的定案。
- 主动提出会改变后续的具体剧情，不把头脑风暴变成等用户逐项安排的问卷或修订清单。
  提问只服务于有实质影响的缺口，不要求每轮提问。用户可以随时改决定。
- 用户讨论与修订次数不限。不要以“五个问题”或固定轮数结束未完成的讨论。
- 用户自己的框架是 `author_brief`；参考样例是 `reference_only`；已有正文是
  `project_canon`。保留作者指定的角色、情节和结局；围绕可拓展部分提出新走线，
  改变已确认决定的方案单独标为备选，不能悄悄覆盖。
- 保留用户选择的真实城市、地域和现实背景；只在用户需要或有明确设计理由时虚构地点。
  发行地域、故事发生地和封面可见地点分别记录，不强制混为一项。
- 不默默修改已确定的姓名、身份、性别或代词。修改必须同步到相关章节和表格。
- 每章应有新的因果或情感价值；前几章强化吸引力，同时保留中后段的揭示与兑现。
- 篇幅、每章范围、序文长度和结局窗口均为可调整的创作目标。合理偏差不阻断交付，
  不为凑字数拉长情节。总章节数、卷边界和命令参数仍需互相一致。
- Sections A-E 是内容组织方式，不是五次独立审批；用户可一次确认完整设计。
  复用已有授权，不以内部流程再次要求同一确认。
- 草稿可随时展示或保存；正式交付完整内容，不用“同上”“后续略”或未替换占位符。
- 模型超时、解析失败或修订失败时保留上一完整版本，说明本轮未完成。
  不用通用模板覆盖已有骨架，不声称未落实的要求“已记录并完成”。
- 默认交付 MD 与命令，不自动启动模型。用户已经明确授权运行时，不再重复索取授权。
- 不自动重启服务、修改模型配置或生成封面。发生封面请求且该 Skill 可用时交给
  `novel-cover-studio`；不可用仍交付封面合同，不阻塞骨架。保留既有交付包流程。

## 3. 整理基础提示

若有工作区，按任务读取 `AGENTS.md`、`CONTEXT.md`、现有 prompt 与所选项目。
只在已有项目修改或续写时读取相关正文、manifest、story bible 和运行状态；
不因为创建一本新书而扫描所有用户作品。给每项材料标记用途：

| 输入 | 用途与处理 |
|---|---|
| 本书的设定、人物背景、原创细纲 | `author_brief`：保留并完善 |
| 参考小说、格式样例、灵感素材 | `reference_only`：按指定用途提炼，不复制独特表达或事件链 |
| 明确选择的已有正文或项目 | `project_canon`：续写和修订以其核实事实为准 |
| 独立要求和新决定 | `user_constraint`：记录适用范围与优先级 |

用途已清楚就继续；只在“保留本书设计”还是“仅参考另创一本”确有歧义时补问。
用简短摘要说明已知设定和关键缺口，不重复用户整篇材料。

## 4. 六类基础信息

从已有材料提取；仅在答案影响当前设计时补问，允许讨论中逐步补齐。
缺少章数、名字等信息时可以先给全书走线，不把完整问卷当作开始创作的前置条件：

1. **章节**：计划章节数；分卷区分总章数与每卷范围，系列区分当前册与全系列。
2. **篇幅**：正文语言、计数单位、每章目标或建议范围、总目标；允许各章不同。
3. **组织形式**：短篇、单部长篇、单本分卷或多本系列。选择长篇后再补问是否拆分；
   已明确“连续写 80 章”就不重新问同一问题。
4. **硬性限制**：必须发生、禁止发生、最早揭示章节、人物关系和结局、尺度、视角与时态。
5. **读者与地域**：目标读者的年龄／人生阶段、阅读动机、发行地域与语言；
   故事发生地另记。“授权群体”在此按“目标受众”理解，除非用户另有说明。
6. **阅读体验**：更希望强化哪些情绪、爽点、悬疑、成长或关系体验，哪些已有选择不动。

用户可委托 LLM 推荐。未获采纳的方案保持提案身份；用户说“按你推荐的来”时，
在委托范围内直接推进并说明选择，不再制造确认轮次。不因缺少装饰细节停止讨论。
正式交付前需明确读者、语言、组织形式、章数及篇幅目标；低影响补充列为假设。
“没有额外硬性限制”也是有效答案。不默认所有作品面向同一种年龄或性别群体。

## 5. 提案与持续修订

按 [story-exploration.md](references/story-exploration.md) 主动创作。初次面对开放构想，
通常提出 3 条因果走线不同的剧情方向，推荐其中一条并说明它如何持续发展。
区别落在事件、人物选择、对抗方式、转折和结局的形成过程，不能只换标签或措辞。
已有明确主线、完整细纲或局部修改范围时，直接从当前设计往前推进，不强迫重选全书。

持续循环：**提出故事机会 → 形成具体剧情 → 结合反馈推进走线 → 检查因果与回报**。
用户说“继续”“不够精彩”时，主动给出新的事件、角色选择与代价及后续影响；
不只反问“想怎么改”，也不每轮重新给三套全书。用户要求收敛或定稿时停止扩散。

按照 [interaction.md](references/interaction.md) 保留版本、已选决定、当前走线或骨架和待定项；
这可以是会话工作记录或文件，不需要新增数据库。用户说“只改第六章”时只扩展到
为维持其改动所必需的依赖；不要顺手重写无关内容。重大的限制冲突需要说明并给解决方案。
探索期展示本轮剧情提案、推荐理由和当前走线摘要，不要求每轮重生成全部 17 节文件。
正式交付时再展开完整骨架与结构合同；已有完整版本不能被简短讨论摘要覆盖。
自动格式修复最多 2 次；仍失败则报告具体遗漏并保留原稿，用户后续仍可无限次修改。

## 6. 完整设计：Sections A-E

这些部分是最终设计的覆盖范围，不是必须逐项询问的表单。先形成“主角目标与主要阻力
→ 关键选择和不可逆转折 → 高潮和结局”的全书因果走线，再展开章表、伏笔与交付字段。
人物只需先明确影响主线的欲望、能力、矛盾与选择；完整档案在走线成熟后补全。
这些部分可以合并展示，也可以分段讨论。只需用户认可整体方向，不要求逐节再确认。

### A. 故事合同与情绪承诺

写出一句话核心冲突、完整梗概、目标读者、读者期待的情绪和回报。
确定主角的外在目标、内在需要、主要阻力、失败代价和结局方向。
以 `ending_contract` 记录主线兑现、主角最终选择、对手后果、情感余韵和允许延续的系列线。
角色的 `required_arc_stage` 使用既有生命周期值；用独立的 `required_outcome` 表示自主、
问责、和解等故事结果，不把结果当作自创 arc stage。

保留 `story_lead_contract`：默认在第一章前安排简短读者序文，中文约 180–260 字、
英文约 120–180 词，仅作建议，可按用户和平台需要调整。以具体冲突、共鸣与回报承诺
吸引读者，不泄露最大反转，不替代第一章自身的开篇。使用既有 `STORY_LEAD:` 标记。

### B. 人物身份、心理与关系

按 [character-and-emotion.md](references/character-and-emotion.md) 建立身份锁定表与心理档案。
包括姓名、别名、性别和代词、年龄、职业、欲望、恐惧、能力、缺陷、底线、隐瞒、
压力反应、做事风格、说话方式，以及人物之间的权力和情感关系。
用“事件 → 理解 → 情绪 → 选择 → 后果”解释重大转折；支持矛盾、迟疑和有原因的反复。
配角有独立需求，帮助有边界，对手会根据失败调整；不要把所有人变成推动主角的工具。
明确 POV、知识边界、时态和文风。心理深度须靠具体经历与行为体现，不只堆积性格标签。

### C. 世界、信息与证据

明确故事地点及真实／虚构政策、时间线、资金与资源、职业与制度约束。
现实题材标出需核实的法律、医疗或职业细节，不编造核实结论；未确认细节写为假设。
幻想题材写清规则、代价与例外。逐项记录“谁知道什么、何时知道、依据是什么”。
证据链包含来源、获取条件、能证明与不能证明的内容、保管与后续验证。

### D. 结构、章节与埋点

按 [hooks-and-payoffs.md](references/hooks-and-payoffs.md) 建立伏笔、钩子、回报和承接表。
给出完整章节细纲，每章含时空与视角、前文承接、目标与阻力、心理与选择、变化与代价、
局部回报、埋设／强化／回收、章末钩子及后续承接。不存在必须在安静章节制造冲突的公式。
前几章分别提供新价值，同时保留后续的发展空间；不能一次用尽全书揭示。
结局窗口按故事容量规划，通常可参考末 3–5 章，不机械套用短篇或每一分册。
最终章兑现主线与情感，可用意象呼应开篇；只保留已确认的系列问题。

篇幅模式必须映射到现有 `[NARRATIVE_FORMAT_JSON]`，读取结构参考后生成真实字段：

| mode | 含义 | 交付与启动 |
|---|---|---|
| `short_novel` | 短篇连续章节 | 一份骨架、一个命令 |
| `standalone_long` | 单部长篇连续章节 | 一份骨架、一个命令 |
| `multi_volume` | 同一本书内部的多个卷 | 一份含卷范围的骨架、连续章号、一个命令 |
| `series_installment` | 多本系列中的当前独立分册 | 系列总纲、每册独立骨架及命令，每次只生成当前册 |

系列总纲定义共享人物、时间线、每册独立回报与跨册伏笔；每册 prompt 自包含所需设定，
不能只让引擎“去看另一个文件”。后册启动前对照前册实际完成状态更新承接。
当前没有 `NOVEL_OS_SERIES` 或 `NOVEL_OS_VOLUMES` 开关；不要编造这类参数，也不要承诺
一条单书命令自动写完所有分册。不在本 Skill 中增加系列调度器。

### E. 设计检查与假设

检查设定保留、身份一致、选择动机、章节完整和连续、早期价值、持续回报、伏笔回收、
结局兑现、模式与字数目标的一致性。存在冲突先修复或明确提出。
设置 `design_review: pass|revise`；正文尚未生成时保持 `draft_review: not_run`。
格式检查、设计审读、材料隔离与正文质量是不同结果，不能互相冒充。

## 7. 输出完整骨架

初始书名只作暂定，不要求用户提前锁定。整体骨架确认后按
[书名设计](references/title-naming.md) 推荐多个候选，允许用户选择、手动修改，或补充要求继续优化。
最终书名以用户决定为准，再同步完整文件与启动命令；已有明确最终命名授权时直接沿用。

使用 [novel-skeleton-template.md](assets/novel-skeleton-template.md) 和
[prompt-contract.md](references/prompt-contract.md)，将最终选择写入完整 17 节文件。
探索期的简短走线不是正式交付，不能用它省略章节、必需合同或校验字段。

- 默认保存 `prompt/<书名或slug>.md`，中文文件名可保留；项目名不能含路径分隔符。
- 用户要求修改已有稿时更新该稿并保留必要版本；未授权覆盖其他作品时使用新路径。
- 顶部保留可解析字段 `Title`、`Author`、`Genre`、`Audience`、`Language`、`Tone`、
  `POV`、`Chapters`、`Words`；总目标按当前册或当前单本计算。
- 每章篇幅写成目标和建议范围，并明确允许合理浮动；不写“严格 500–600 words”
  等可能被现有扫描误认为硬边界的表达。需要改变已给定硬性字数规则时先遵守用户最新决定。
- 输出恰好一份 canonical `[NOVEL_CLASSIFICATION_JSON]` 和一份已确认的
  `[NARRATIVE_FORMAT_JSON]`；活跃商业配置另带 `[COMMERCIAL_STORY_JSON]`。
- 保留 `audience_profile`、与用户选择相符的 `setting_policy`、selected-only
  `workshop_trace`、人物／关系／秘密／时间线／资源表、序文与结局合同。
- 保留既有 `Payoff_Events`、`Arc_State_Updates`、`Personality_State_Updates`、
  `Ending_Evidence` 的生产提示协议；参考合同负责字段细节。
- 加入一个严格 JSON 的 schema-v2 封面交接块，使用 `COVER_HANDOFF_BEGIN` 与
  `COVER_HANDOFF_END`。内容来自 Sections A-E，不添加未确认的人种、身份或剧情。
- 在 `COVER_HANDOFF` 中可选加入轻量 `cover_constraints`，只记录已确认的故事事实边界、
  用户指定的故事节点或人物、禁止出现的内容、剧透上限、用户视觉偏好与来源引用。
  它是交接约束，不是封面方案；不要在头脑风暴阶段生成 `candidate_moments`、人物构图、
  动作、镜头、光线、视觉钩子、图片提示词或 3–5 个封面方向。
- 封面时刻选择、人物视觉层级、动作与反应、scene/campaign_composite、构图、标题布局、
  封面方向和质量评估全部归封面工作台负责。`COVER_HANDOFF` 是压缩事实投影，不能替代
  封面工作台的完整骨架快照与来源分析；同一 source digest 的分析应由工作台缓存并复用。
- 正文交付不包含推理草稿、未选提案、来源对比或内部 Agent 评论。

可以复用本项目已批准片段校准文风；必要时给简短原创样本并标为“风格示例，非正文事实”。
不把设计任务扩大成写完整章节的额外审批流程，不使用参考作品原文作模仿样本。

## 8. 自检、命令与交接

读取 [launch-command.md](references/launch-command.md)，按实际路径使用
[scripts/handoff.py](scripts/handoff.py) 的 `validate` 和 `command` 子命令。
从仓库调用的形式如下；实际执行前将占位路径和项目名替换为真实值：

```bash
python3 skills/novel-brainstorm-workshop/scripts/handoff.py validate './prompt/BOOK.md' --repo .
python3 skills/novel-brainstorm-workshop/scripts/handoff.py command './prompt/BOOK.md' --repo . --project 'PROJECT'
```

安装到外部 Skill 目录时使用脚本实际路径并显式指定 `--repo` 的仓库位置。
辅助脚本只检查元数据、已有类型／结构合同及命令一致性，不检查故事内容是否完整。
