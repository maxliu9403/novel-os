# 主动共创、提问与无限修订

## 先提取，后补问

使用用户的语言交流，正文语言另记。将已有材料中的章节、字数、模式、限制、受众地域和
希望的阅读体验先归一化。不要要求用户再填一遍长表。确需补问时集中处理少量
有实质影响的问题，可提供短选项，也允许自由回答；并非每轮都需要提问，没有总次数上限。
信息足以提出剧情时先主动创作；当前不影响走线的细节留到后面，不逐项等待用户填空。

核心选择不明确时可以给建议和草稿，标为待定。用户已有明确选择即是确认；
“你推荐一个”允许提案，“按你推荐的来”允许直接沿用，不再人为制造确认轮次。
次要姓名、地点、职业细节可提出带标记的假设；若名字已给出，直接锁定。

读者、发行地域、正文语言、故事发生地分别记录。无法决定发行地域时允许用户明确选择
“泛英语读者／不限单一地域”，不要强行默认美国；地点是否真实由故事设计和用户决定。
没有额外硬性限制可以记为 `none`，空白不能悄悄当作没有限制。

## 提案

先区分硬限制、已确认决定、可拓展草纲和空白。作者提供的初步想法值得发展，
不等于每个暂定事件都已锁死；明确要求保留的内容仍须保留。
按 [story-exploration.md](story-exploration.md) 为开放构想主动提出不同因果走线，
初次通常给 3 个剧情方向并推荐一条。已有细纲则寻找尚未充分发展的冲突、人物选择、
对手反应或伏笔回收，给出可接入当前故事的剧情，不要求作者放弃自己的框架。

用户选择后持续推进当前路线。“继续”“不够精彩”应得到具体的新事件、选择、代价
和后续影响，而非只得到问题、评价或“加强爽点”的抽象建议。不同方向的数量按实际
分歧决定，不每轮重复给三套全书；局部修订或定稿请求不强行扩散。
拟改变已确认决定时标明备选与取舍；用户委托按推荐推进时，在授权范围内直接落实。
尚未采纳的提案与当前选定路线分开保存，未选方案不进入运行上下文。

## 工作记录

保留可观察的决定和摘要，不保存或展示隐含推理过程。可使用会话记录或普通文件：

```yaml
workshop_state:
  version: 3
  status: draft  # draft | ready_for_review | confirmed
  current_skeleton_path: null  # 有文件时记录真实路径
  material_use:
    - id: author_outline
      label: author_brief
      preserve: [characters, ending, no_confrontation_before_ch6]
  confirmed_decisions:
    - id: decision_001
      field: narrative_mode
      value: multi_volume
      source: user_explicit
  pending_proposals: []
  open_questions: []
  revision_summary:
    request: 把正式摊牌延后到第六章
    changed: [chapter_3, chapter_4, chapter_5, chapter_6, reveal_001]
    retained: [character_identity, ending]
  checks:
    design_review: revise
    parser_review: not_run
    draft_review: not_run
```

早期的当前稿可以是全书走线与主要转折，不必伪造一份完整骨架。版本是当前稿状态，
不声称 Web 已有持久化会话数据库。可保存时采用独立工作目录中的
版本稿与决定摘要，避免覆盖别人的作品。已有同一任务的编辑授权支持继续更新当前稿。
最终运行 prompt 只带 `workshop_trace` 的当前已选决定、来源无关假设与必要设计依据。

## 每轮执行

面向作者的每轮回复使用 Markdown。较长回复用简短三级标题分段；段落间空一行，
方向建议、修改清单和待确认项分别使用列表，关键区别可加粗，需要比较时才使用表格。
短回复可以只用一个简短段落或列表，不堆空标题。不要把完整回复包在
`markdown` 代码围栏中，不输出原始 HTML；宿主要求 JSON 传输时，回复字段保存完整
Markdown 文本，JSON 外壳由宿主处理。折叠摘要只影响界面展示，不删减已保存的完整内容。

先判断本轮意图，再选择合适的工作；不把所有请求都变成同一张检查表：

- **探索或继续发展**：主动提出具体剧情与推荐理由，说明人物选择如何带来后果、
  对手如何反应、哪里产生新的问题或兑现已有承诺。简短更新当前全书走线。
- **明确修改**：落实用户要求，检查受影响的因果、身份、知识、章节、伏笔和结局，
  展示变化及必要影响；保留无关决定。简单修改可以直接完成，不追加提问。
- **比较或答疑**：围绕用户问题解释剧情差别与取舍，不借机强制推进新分支。
- **收敛或交付**：停止增加无关方向，补全已选故事的章表与必要设计，
  执行交付检查，展示完整骨架及命令；复用已有确认和授权。

探索期回复以故事内容为主：新剧情、推荐理由、当前走线与真正需要决定的分歧。
只在内容需要时使用这些标题，不强制凑齐。完整骨架可按用户要求随时预览，
但不每轮重发或重生成 17 节；保留已有完整版本，摘要不替代正式交付。
检查主要因果与硬限制即可，不把措辞、道具外观、对白打磨等正文细节提前变成阻塞项。

例：用户说“她在第六章前不能摊牌”，检查前五章对话、公开指控、对方知情时点、
证据收集、情绪转折和钩子，而不只是把标题中的摊牌改掉。
用户将女性角色改为男性时，更新身份表、代词、关系称呼及确实受性别影响的情节；
保留其原有能力和性格，不自动套用性别刻板印象。
章节数减少时，重新分配伏笔与回报，不能只截掉后几章；模式改变时重建卷范围和命令。

## 异常与完成

基础设定可随时回看，未启动的任务在推导空闲时可修改。保存更改时保留旧骨架和历史，
记录变更并重新推导；已有书名与启动命令需要按新骨架重新确认。已启动任务保留启动快照。
骨架确认后的命名遵循 [title-naming.md](title-naming.md)，不把暂定名当作最终授权。

模型调用或解析失败：保留上一完整版本，显示失败与未应用的修改；成功修订后再替换当前稿。
不得用通用骨架顶替，也不得声称本轮建议已经落实。
自动纠错最多两次；仍失败则明确指出问题，让下一轮围绕实际问题继续。用户轮次没有上限。

只要用户明确认可整体设计，即可输出正式文件；Sections A-E 无需五次单独批准。
最终自检发现机械遗漏可以直接补齐；若需要改变用户认可的结局、人物或主要方向，
说明具体矛盾并保留当前稿，不能代替用户做相反选择。
骨架改动后将旧启动命令标为过期，重新由当前版生成。交付文件与命令不等于授权运行。
